# Mac 网络流量采集探查与接入方案

状态：2026-10-09 已按用户选定的方向部署代理流量采集、缓存补传及统一查询；应用归属接入仍待完成。Token Monitor 仅参考把采集任务打包并由客户端管理的方式，网络采集复用本仓库现有 ShellCrash 口径。

## 已验证的接入点

- 本机 Clash Verge 的 Mihomo v1.19.31 正在运行。实际 API 使用 `external-controller-unix`，TCP 9097 未监听；采集器必须读取正在使用的配置并支持 Unix socket。
- 本机 `/connections` 只读请求成功。一次快照共 152 条连接，152 条有上下行计数和路由，127 条有域名，应用名与进程路径全部为空。相隔一秒的两次请求观察到计数增长及连接新建、关闭。上述数量仅代表该次快照。
- 本机运行模式为 `rule`，进程识别为 `strict`，TUN 与系统代理开关均关闭，Proxifier 正在运行。现有接口可以覆盖经过 Mihomo 的代理连接，不能据此声称覆盖全机网络。
- NAS ShellCrash 采集服务正常运行。现有采集器每秒读取 Mihomo `/connections`，每十秒落 SQLite 小时累计事实，并记录采集缺口；归档服务每十五分钟同步。
- NAS 与 Mac 使用相同类型的 Mihomo 明细，可复用小时、目标 IP、域名、进程、来源 IP、策略组、流量池、订阅源、出口节点、规则、上下行字节字段。

## 需要先解决的问题

1. **应用归属缺失。** 临时将进程识别改为 `always` 后，27 条新连接仍全部没有应用名；原配置已恢复。2026-10-10 已核对 Proxifier 界面及普通、详细文件日志：有应用名称、目标、代理和连接关闭时上下行字节，但没有可与 Clash 对应的连接 ID 或源端口。1,468 条元数据事件中，24 个目标由多个应用访问，同一秒同目标重复 89 次，不能用域名与时间猜测归属。日志位于管理员目录，已恢复原先关闭文件日志的设置。当前 Clash 来源保留“未知应用”。
2. **统计范围。** 默认接入现有代理链路，界面明确标注代理流量。绕过代理的直连流量不在该明细口径内。若要求全机明细，需要另行评估系统级采集与权限，不能通过本机代理快照补出。
3. **跨采集位置重复。** 同一访问可能经过 Mac 与 NAS，两层字节数不能直接相加。统一数据必须保留设备和采集位置，并按位置汇总。两个内核的连接 ID 不能当作跨设备去重依据。
4. **已有轮询误差。** 每秒读取活动连接会漏记采样间隔内完成的短连接及关闭前的尾部字节。复用该方式时应保留采样口径、缺口状态，不声明账单级精确流量；后续改进采集方式需同时核对 NAS 与 Mac。
5. **展示缺少明细。** 现有服务端网络展示索引仅提取上传和下载；客户端新增采集后还要补设备、应用、域名、路由维度展示，才能满足需求。

## 已实施的接入

客户端打包本仓库维护的采集代码与运行时，新增固定 `--collect-network` 后台入口。与微信、活动采集一样由客户端安装并管理 launchd 任务，关闭主窗口后继续采集，设置页面显示启用状态、最后采样、最后上传及缺口。首次启用自动识别本机代理的 Unix socket，后续随运行配置重新发现路径。

本机每秒先写私有 SQLite 和上传队列，每分钟使用已配置的 NAS SSH 通道同步；`hub ingest-network` 校验来源身份、批次哈希和限定字段，落库成功才回执。本机只清除与回执内容哈希相同的待传版本，上传期间发生的更新仍待传；失败保留记录。小时累计值按稳定键覆盖，延迟重试不能降低服务端已提交计数。重启、休眠和断线显式记录缺口，缺口期间的字节不虚构归入恢复后的小时。

服务端保留现有 ShellCrash 来源和历史，为 Mac 注册独立设备来源；两者归入同一网络模块。`GET /api/v1/network` 按所选采集位置提供上下行及应用、域名、策略组、节点排行。客户端增加网络流量页面与设置中的后台采集开关、最近采样/上传、待传数及异常提示。默认概览只选择一个采集来源，避免叠加两层观测。应用归属尚未补齐。

## 数据契约影响

归档库复用现有 `raw`、`normalized` JSON 和来源注册机制，未迁移数据库表。扩展载荷与展示索引契约如下：

| 字段 | 用途 |
| --- | --- |
| `device_id` | 本机固定设备身份，重启和应用更新保留 |
| `collector_id` | 标识具体代理内核采集入口 |
| `measurement_scope` | 首版为 `proxy` |
| `measurement_point` | 区分 Mac 终端与 NAS 代理层 |
| `host`、`process`、路由字段 | 现有原始事实字段，增加可查询展示维度 |
| 采样及缺口状态 | 区分零流量、采集停止和来源不可用 |

小时键与外部记录身份包含设备及采集入口。旧 NAS 数据按既有来源解释，保留原记录 ID 与字节数。Mac 不写入现有 `shellcrash` 来源，避免覆盖旧事实。

## 验收条件

真实新连接能验证应用归属，若只能识别代理进程或仍为空，则明确反馈该限制；不能以接口成功代替应用归属验收。后台持续采样、休眠/重连缺口、断网后补传和相同批次重试分别验证。客户端与 NAS 按同一设备、小时、域名、路由读取回执后的字节数一致；在页面切换采集位置不会把同一链路两层观测重复相加。

## 当前验证

客户端 0.3.5 build 14 已安装，签名与固定凭据助手保留。后台代理 API 访问检查成功，launchd 网络任务运行；NAS 网络只读接口返回 HTTP 200。真实小时事实上传后可通过统一查询读取，Mac 与 NAS 分别选择统计。离线三个用例覆盖计数基线/增量/重置、失败重试与上传竞态、跨小时恢复缺口、重复/乱序回执及来源隔离；原应用组件五个检查通过，NAS 展示冒烟通过。

2026-10-10 解锁后的实际验证：本机今天已结束小时的 1,713 条事实与 NAS 原始记录逐条完全一致；后台最近采样、最近上传持续推进，成功上传后队列归零。客户端选择本机来源可显示上传、下载、域名、节点及策略组，切换日期时出现加载提示；设置中网络采集已启用，应用归属缺失有明确提示。Command＋W 后同一 GUI 进程由 Foreground 转为 UIElement，网络 launchd 任务继续运行、采样继续推进。

NAS 旧网络记录的展示索引未包含新维度，抽样 500 条原始事实均有 host/process 字段，旧索引中均缺失。已使用仅限 `traffic_hourly` 的重建流程修复，核对时 45,014 条网络事实全部有展示索引。Mac 与 NAS 只读接口均返回 HTTP 200，当日总计分别与原始记录求和完全一致。NAS 应用维度恢复为 16 组（其中 15 组已知），域名、出口、策略组明细恢复；Mac 应用仍未知。未迁移数据库表。

## 应用归属的后续接入影响

本机流量先经过 Proxifier，再进入 Clash；同一链路不能注册成两份可汇总的流量来源。本机继续使用现有 `network-mac-<device_id>` 来源，Clash 提供字节、域名、节点及策略组，Proxifier 仅作为应用识别的辅助元数据。统一记录只计一次字节，不另建 Proxifier 流量统计。

应用补全尚未实施。前提是找到可靠的连接对应关系；当前普通、详细日志缺少与 Clash 共同的连接标识，不能仅凭同域名或同一秒访问合并。未建立可靠关联时保留未知应用，不把 Proxifier 的关闭字节作为第二份流量写入归档，也不声称现有方案已满足应用归属。

若最终需要持续读取 Proxifier 管理员目录日志，需先反馈固定路径读取组件与一次管理员授权的接入影响。现有完全磁盘访问权限并不能让普通用户读取 `/var/root` 下日志。辅助组件仅服务于应用映射，后续设计仍需解决关联标识、日志轮转和覆盖状态；本轮未启用该组件。不能据现有日志承诺每个应用对应的 Clash 出口节点。
