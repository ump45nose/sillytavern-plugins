# 刷新期限配置与部署记录（2026-10-05）

应用清单新增 `refresh_token_lifetime_days`，省略时默认 **180 天**。本次 CRM、远程工作台、Media Download、邮件、钉钉全部采用默认；访问令牌的原短期限保持不变。

## 改动与部署

- 公共运行时及部署 CLI 升级为 0.1.3。运行时从清单生成的 `OAUTH_REFRESH_TOKEN_LIFETIME_DAYS` 取得代理刷新凭据期限。
- Authelia 为四个客户端生成独立的 `mcp_platform_<client_id>` lifespan；保留原客户端 ID、密钥、回调、策略、模板、issuer 和 28443 端点。候选经过官方校验、部署锁及摘要比较后生效。
- 钉钉继续使用 MCPHub；`oauth_provider: mcphub` 将北向 OAuth 的 `refreshTokenLifetime` 设置为 15552000 秒。共享设置更新时短暂停止进程，回滚只恢复期限字段，保留新令牌与注册信息。
- CRM、邮件与 Media OAuth 网关复用原镜像，注入宿主机构建的 0.1.3 wheel 后更新；没有构建或替换业务后端。wheel、源码及原／新镜像摘要保存在仓库外私有运行记录中。
- 远程网关仍采用原独立认证装配，应用 `integrations/local-env-mcp/refresh-policy.patch` 从同一 env 设置读取期限；未重启执行器。现有网关 env 及重载命令通过 NAS 私有目标的 `auth_runtime_env_files`／`auth_reload_commands` 登记。
- 五个原生网页 App 均在原账户上重新授权，保留原 App ID、名称、图标、域名、签名／加密密钥和 OAuth 存储。没有创建新插件或恢复旧包装 App。

## 后续操作

1. 修改业务 `mcp.app.yaml` 的 `refresh_token_lifetime_days`；省略即使用半年默认。
2. 用 `mcpctl plan <app> --target nas` 检查提供方、期限与变更。构建模式正常部署会注入同一期限；已有网关由私有 env／重载绑定协调。
3. 运行常规 `mcpctl deploy`；仅协调提供方或已绑定网关认证配置可用 `--auth-only`。无差异跳过重启。
4. 新配置不延长已签发令牌。需要立即采用新期限时，在原 App 重新授权，再核对新时间元数据和一次只读调用。

此前邮件及 Media 新客户端缺少 lifespan，Authelia 实际刷新期限仅 90 分钟；FastMCP 默认代理凭据期限却为一年。部署必须同时验证上游和代理期限，不能仅以首次登录成功判断隔夜可用。
