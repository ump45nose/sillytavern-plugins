# CRM 架构与逻辑复查

## 范围与阶段

按“个人自用，最终信息供用户和 AI 直接读取”审查独立仓库 b22dd6f、当前 Mac 读取器和 NAS 实际运行入口。本轮仅审查、只读查询和临时目录内复现；没有修改业务代码、线上数据或部署。

审查覆盖人物/交互模型与 CRUD、微信增量与分段、媒体读取/补传、HTTP/MCP 装配，以及独立源码与生产宿主的差异。完成条件是区分必要机制、可删除的复杂度和有证据的缺陷，并给出收敛方向。

## 结论

保留“采集器 → 归档 ← HTTP/MCP”的三层，以及人物、交互、附件、来源身份和去重回执。问题集中在附件可用性的定义、媒体同步重复逻辑和未独立的生产装配，不需要重造人物模型或引入新平台。

业务正文和附件不增加加密层。现有代码没有主动加密图片，而是照搬微信加密 dat；将其计为可用附件，不符合产品目标。

## 必须修正的逻辑

### 1. 加密缓存被当成可用附件（高）

- connector/media_reader.py:197–210 原样上传 dat，标注 application/vnd.wechat.encrypted-image；archive/service.py:634–641 只检查文件是否存在。
- 从实际归档读取此前展示的图片，文件为微信 V2 格式；Pillow 打开失败，UnidentifiedImageError。此前文件下载 200 不能证明图片可读。
- 本机依赖已有 decrypt_wechat_dat；其 V2 路径需要已有图片密钥缓存。本轮未调用解密函数、未读取密钥值，也没有验证两台 Mac 是否都能转换成功。
- 方向：采集端完成微信格式转换，只上传能正常打开的普通图片/音频/文件。归档端不管理微信密钥，不保存加密原文与可读副本两套内容。转换失败直接说明未取得可用文件，不能计为完成。

### 2. 普通文件消息会漏采（高）

- connector/sync.py:61–74 用 attachment_meta.file_name、sub_type 或原始 XML 判断 49 类文件消息。
- 实际 native message-stream 记录没有这些字段，正文已经变成文件占位；采样一条真实文件消息，sync_once(dry_run=True) 的 attachment 为 null。
- 只读查询旧私聊记录：721 条 49 类消息，80 条有文件占位；attachment_meta 与 sub_type 均为零。80 是候选记录数，不是已核对的独立文件数。
- 当前归档没有普通文件类型的附件。这说明之前“剩余 88 个未取得”只覆盖已经建了附件条目的集合，不能代表所有文件消息都已纳入。
- 方向：补齐读取器到采集器的明确附件元数据契约，不再从简化正文猜附件类型；历史文件消息也需要纳入修复清单。

### 3. checkpoint 损坏会静默跳过未同步区间（高）

- connector/checkpoint.py:10–15 把不存在、损坏和其他读取错误都变成空对象；connector/sync.py:31–37 随即按当前时间初始化并覆盖原文件。
- 临时目录复现：损坏 checkpoint 被替换为当前水位，errors=[]。
- 方向：仅文件不存在表示首次启用；损坏/无权限直接报错，不能修改水位。已有服务端设备水位可用于明确的恢复操作，无需新恢复框架。

### 4. 媒体存在第二套增量边界，而且完成后仍重复入队（中）

- connector/media.py:40、48–68 保存独立 enabled_since，并丢弃更早的媒体；新启用媒体时，首轮文字增量可能早于这一时间。
- 复现：同一条消息正文 accepted=1，但 media_jobs=0。
- connector/sync.py:88–104 对重叠窗口的全部媒体入队，服务端仅返回计数；完成任务删除后，同一条重复消息会再次创建任务。
- 复现：服务端 duplicates=1，已完成媒体仍 requeued=1。队列同时保存整份 record.content，但读取媒体只需账号/会话/消息定位。
- 方向：只有一个消息同步水位。批量写入回执告知本批仍缺的附件，采集器只处理这些；保留一个未完成附件列表及必要重试信息，不保存正文。

### 5. 日期和精确时间可以互相矛盾（中）

- archive/service.py:319–336 验证时区/先后，却没有统一 date 与 started_at；451–470 的查询同时依赖 date 和结束时间。
- 临时库复现：date=10月1日、started_at=10月16日被接受，按10月16日查询结果为零。
- 方向：有精确开始时间时统一按 Asia/Shanghai 派生 date，PATCH 开始时间同步更新日期；只有日期的交互继续不伪造时间。

## 架构收敛

### 生产入口还没有独立

NAS 当前镜像 local/personal-data-hub:crm-readable-20261016-r2，启动命令为 personal-data-hub。其 personal_crm.app.server 仍装配 Hub、日报和事件模块，与独立仓库同名模块不同，配置也仍使用宿主字段。独立仓库发布完成，不代表生产装配已经独立。

推荐生产直接运行独立 CRM 包；仍需消费 CRM 的其他系统通过接口读取，保留其他来源自己的运行职责。发布应使用同一个 CRM 源码产物，而不是重做同版本的宿主兼容包。

### 数据库与模块依赖可进一步收敛

当前维护 SQLite/PostgreSQL 两套锁、JSON 搜索和时间表达式；原方案沿用现有 PostgreSQL，建议固定 PostgreSQL，不为通用发行维护另一套运行路径。

archive/service.py 与 migration.py 反向导入 connector.presentation；应将归档行格式放回归档模块，必要的纯文本辅助函数放共同模块，采集器只承担来源读取与文件转换。保留 Archive 一个业务入口，不增加 Repository/Manager/Workflow 等中间层。

## 建议落实顺序与验收

1. 可读附件和普通文件漏采：图片实际打开、音频实际解码、文件实际读取；不以文件存在或 HTTP 200 代替。
2. 合并媒体与消息增量：首轮新增媒体不漏；重复消息不再次上传已存在附件；失败后仍可补传。
3. 修正水位错误与日期一致性：损坏水位不被覆盖；精确时间对应日期能查询到。
4. 用同一独立产物收敛生产入口，移除不再需要的双数据库和宿主兼容逻辑。

保留必要的来源身份、增量去重、事务、分页、原有认证和未完成附件重试。不开设加密系统、原文/归纳双副本、审批、额外服务或全量同步。
