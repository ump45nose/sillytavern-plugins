## 按优先级排列的发现

### R1 · P1：shell 入口替换青龙进程，任务无法收尾

位置：[checkin_runner.sh](/vol2/1000/Docker/qinglong/data/scripts/checkin_runner.sh:2)，尤其第 5–7 行的 exec。

运行中的青龙将 .sh 设置为 `which_program="."`，即 source 到任务 shell 中。入口的 exec 会直接替换这个 shell，后面的 run_task_after、clear_env 和 handle_task_end 都没有机会执行；set -eu 同样会污染调用它的 shell。

实际证据：V2EX 283、阿里云 284 的数据库 status 均为 0，last_running_time=0，保留早晨 pid；16:21 查看青龙进程已没有对应任务进程。使用当前入口文本、只替换为本地无网络假任务，复现 `child_finished=true`、`scheduler_end_hook=false`、退出 0。

建议：移除这层 source 型分发，青龙直接调用已有 venv Python 和各来源入口；或者改为不使用 exec/set -e 污染父 shell 的薄入口。更新时同时迁移日志定位，避免旧日报仍固定读取 bin_python。修复后只需用无副作用任务验证青龙能完成收尾，不用再次领取奖励。

### R2 · P1：公开版 V2EX 将真实失败报告为进程成功

位置：[checkin.py](/home/yuwk/benefits-public/v2ex-dailycheckin-ql/checkin.py:24)。

公开入口直接调用 dailycheckin.main.checkin()。当前已安装的上游 CLI 会捕获账号异常、打印失败，随后正常 return；包装层没有检查业务结果。无网络复现使用真实上游 CLI，只替换 provider 为抛异常的假实现，得到 `provider_failure_logged=true`、`public_entry_exit_code=0`。

线上 [v2ex_checkin.py](/vol2/1000/Docker/qinglong/data/scripts/v2ex_checkin.py:8) 已有超时、代理和失败退出逻辑，发布时却重新实现了一个更弱的入口。这是源代码副本分叉已经造成的实际回退。

建议：以现有线上 provider 入口为基础清除固定代理地址后发布，明确返回签到结果和非零失败码，保留“连续天数查询失败不抹掉已确认奖励”的语义。不要再增加一层通用上游 CLI。

建议：先将 laowang 的现有会话迁到独立来源目录并验证能读到登录态；日常执行采用一次性 headless 浏览器。交互登录/VNC 作为按需入口。之后才能退役旧 FGC worker 及其旧 Epic/Rewards 路由。

### R7 · P2：CookieCloud 同步依赖另两个私人项目，平台失败还会互相阻断

位置：[cookiecloud_env_sync.py](/vol2/1000/Docker/stacks/qinglong/benefits/qinglong/cookiecloud_env_sync.py:11)。

同步脚本通过固定 sys.path 导入 favsync.cookies 的私有函数 _selected/decrypt，以及 qinglong-setup 的 ql_api；密钥路径也归属 favsync。迁移或升级其中任一项目会影响签到凭据同步。Aliyun 和 JD 在同一个 main 内串行执行，只有最外层异常捕获，前一平台的请求异常会阻止后一平台执行。日志中确有 URLError 和认证失败记录，但没有逐行时间，不能据此精确断言每次失败属于哪一天。

建议：把 CookieCloud 解密和青龙 API 调用收敛到一个独立凭据同步入口，按平台隔离异常；保留已有 CookieCloud 服务，避免新增服务或数据库。只记录更新时间和认证状态。当前阿里云必须另行验证同步源中是否还有有效凭据，重构本身不会修复失效 Cookie。

### R8 · P2：日报依赖固定 cron ID、日志目录和输出文案

位置：[benefits_daily_summary.py](/vol2/1000/Docker/stacks/qinglong/benefits/hermes/benefits_daily_summary.py:20)。

汇总同时依赖固定 ID、bin_python/fgc/rewards_entry 目录，以及“全部成功”“每日登录奖励”和 JSON 字段顺序等文本。重建 cron、改命令或格式化输出，就可能把真实执行变成无记录。--date 回看过去时还先检查今天的 isDisabled，因而现在禁用某任务会把过去的已执行日改显示成“未启用”。

Rewards summarize.cjs 还能输出 eligible-tasks-complete-with-restrictions，但汇总只处理 partial/complete，会将这个成功但受限的状态落为“待核实”。当前未命中此分支，属于可确定的状态契约缺口。

建议：每个来源追加自己的结果 JSONL，至少包含 platform、business_date、finished_at、run_id、success、reason；Hermes 只读该接口。定时是否启用作为“当天无记录”时的补充信息，不覆盖已有历史结果。不要让消息推送层解析平台日志或内部数据库结构。

### R9 · P2：超时处理会抛出第二个异常，丢失超时状态和暂停计数

位置：[worker.py](/vol2/1000/Docker/stacks/qinglong/benefits/worker.py:156)。

subprocess.TimeoutExpired 中已经捕获的 stdout/stderr 可能是 bytes，即使 subprocess.run 使用 text=True。当前代码将它们与字符串换行拼接，产生 TypeError。离线复现结果：`TypeError: can't concat str to bytes`，state 文件没有生成。外层最终会留下普通失败结果，但 task_timeout、证据和连续失败暂停逻辑都被绕过。

建议：在统一输出边界将 bytes 解码为字符串；确保超时也经过相同的状态和结果持久化流程。一个带部分 stdout 的超时冒烟即可验证。

## 推荐清理顺序

1. 修复 R1、R2、R9 的明确逻辑缺陷；先保证任务退出和报告可信。
2. 从默认启动移除 QD、中国移动；删除废弃 Cron 291 的汇总分支。保留数据以便回退。
3. 迁出 laowang 后退役 FGC 常驻浏览器及旧平台路由。
4. 为各来源确定唯一源码和固定部署版本；收拢凭据同步依赖。
5. 将 Hermes 日报改为读取小型统一结果接口，再移除日志解析和多份任务配置。

目标：青龙负责执行时间，各来源负责业务与自己的登录态，Hermes 负责发送结果。轻量脚本直接执行；浏览器依赖独立运行。共享部分只限结果格式、配置传入方式和部署清单，不再增加一个大而全的签到框架。
