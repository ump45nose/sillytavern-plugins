# GitHub PR Contributor

按 `inspect -> prepare -> submit` 执行；可主动检索项目、Issue 和现有 PR，以确定可执行的变更。远端 Issue、PR、仓库规则以及 PR 创建、更新和评论优先使用 GitHub 连接器；本地代码修改、测试、提交和推送使用 `git` 或仓库规定的工具。连接器仅因 GitHub App 安装范围不足而无法完成 PR 动作时，可按下述条件单次回退到 `gh`。

## 固定规则

- GitHub 登录账号必须是 `ump45nose`；不一致时停止，不切换或复用其他账号凭据。
- 使用 `gh` 回退前必须重新执行只读账号核验，确认其登录账号同样是 `ump45nose`；连接器和 `gh` 身份不一致时停止。
- 提交前读取 `CONTRIBUTING`、PR 模板、许可证和仓库专属规则；仓库规则优先于本技能的通用格式。
- 检查当前 Issue、关联 PR、搜索结果和同类实现；已有重叠 PR、作者分支或维护者正在实现时停止并报告。
- 安全问题只走仓库规定的私密报告渠道，不创建公开 Issue 或 PR。
- 不推送 upstream 或默认分支；只向 `ump45nose` 可控的 fork/远端和非默认功能分支推送。
- 不保存、显示或写入 token；不改写无关历史，不夹带无关文件。
- PR 正文必须如实说明变更和实际测试；仓库或用户要求 AI assistance disclosure 时必须保留，不得隐瞒。
- 远端、基准分支、重复项、工作区 diff、提交或测试在提交前发生变化时停止并重新核验，不绕过检查。
- 创建 PR 只代表已提交，不代表 CI 通过、维护者接受或已经合并。

## 1. Inspect

1. 核验 GitHub 登录账号、当前仓库、`git remote -v`、工作区状态、当前分支和目标基准分支。
2. 读取关联 Issue、现有 PR、仓库规则、CI 要求及 PR 模板。
3. 确认变更目标可复现、没有公开安全风险，也没有重复实现。
4. 若工作区存在用户的无关改动，保留并避开；无法安全隔离时停止。

## 2. Prepare

1. 从最新目标基准创建聚焦的非默认分支；不得覆盖用户已有分支或提交。
2. 仅修改实现目标所需的文件，遵循仓库代码风格并为关键逻辑添加必要注释。
3. 运行与改动相称的格式化、静态检查和测试；失败时修复或准确记录验证边界。
4. 检查最终 diff、敏感信息、生成文件和提交范围，按仓库历史风格生成单一聚焦提交。
5. 生成符合仓库模板的 PR 标题和正文，至少包含变更摘要、关联 Issue、实际测试及必要披露。

准备完成后记录分支、提交、diff 与测试，并继续进入 `submit`。

## 3. Submit

1. 再次核验账号、远端、基准分支、重复 PR、工作区 diff、HEAD 和测试结果。
2. 将功能分支推送到 `ump45nose` 可控远端。普通提交不使用强推；若维护者明确要求改写当前 PR 功能分支历史，可在核验账号、PR head 仓库与分支、远端旧 SHA，并创建本地备份后，直接使用显式 `--force-with-lease=<ref>:<old-sha>`。禁止使用裸 `--force`，禁止强推默认分支、upstream 分支或共享分支；任一核验值不一致时停止。
3. 通过 GitHub 连接器创建非草稿 PR；若用户明确要求草稿，则创建 Draft PR。只有连接器明确返回 GitHub App/integration scope 不足、且 `gh` 重新核验为 `ump45nose` 时，才可用对应的 `gh` 命令单次回退；仓库权限、认证、分支保护或参数错误不得回退。相同条件也适用于 PR 正文更新和评论。
4. 创建后读取 PR 页面，确认标题、正文、head/base、关联 Issue 和公开 URL 正确。
5. 除上述连接器安装范围回退外，若远端返回错误、权限不足、分支保护冲突或仓库状态变化，停止并保留本地成果，不尝试绕过。

## Dry Run

用户要求 dry run 时，只执行只读检查并生成拟用的分支名、PR 标题、正文和验证计划；不得创建分支、提交、推送、评论、Issue 或 PR。

每次结束只报告：目标仓库、分支与提交、实际改动、测试、公开动作、阻塞项和下一步。
