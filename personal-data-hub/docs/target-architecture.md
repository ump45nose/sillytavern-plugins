# Personal Data Hub 采集加工优先的全局架构与开发指引

日期：2026-10-12。状态：全局指引，以最新实施范围为准。用户明确：微信模型提炼暂缓，作为后续分析模块的目标统一设计；Mac 接入不阻塞服务端收口或后续开发。

当前核心是把采集能力做完整：已经取得的原始信息必须经过加工，成为用户能直接浏览、检索、理解并追溯的信息。数据入库、生成短预览、提供原始 JSON 查询，都不能单独代表采集侧完成。

执行顺序固定为：**先加工现有原始信息并完成可读展示；再固化后续数据接入流程、按该流程补齐采集侧；采集侧验收后再开发增量产品；最后将成熟能力包装为标准 API、MCP 和 MCP Events，接入 Bot。**

当前原始信息加工先完成确定性整理、完整阅读和检索，复用来源已有的摘要。Hub 微信模型主题/要点提炼已经暂停，移到后续分析模块统一设计。最终视觉风格可留给 Figma，当前的阅读层级、正文组织、时间线和内容控件必须现在解决。

执行分工（2026-10-11 用户澄清）：本对话只实现和验证服务端；客户端由用户在 Mac 开发。每个需要客户端配合的节点交付 `docs/client-requirements/` 中的接口、控件和验收需求。服务端节点通过后可继续下一服务端节点，不等待本对话执行 Mac 编译；服务端独立收口；客户端联调与真实阅读体验单独登记，不作为服务端后续开发的前置条件。

## 1 优先级与阶段边界

| 阶段 | 首要交付 | 完成条件 | 后续工作的边界 |
| --- | --- | --- | --- |
| 一 现有原始信息加工 | 按来源处理已有数据，形成可读内容、聚合结果、索引与客户端展示 | 本轮现有来源逐类通过真实内容的阅读验收，并覆盖更新、删除和失败情况 | 不启动新的记忆、目标、分析建议或 Bot 接入项目 |
| 二 固化接入流程并补齐采集侧 | 从第一阶段实际实现提炼接入规范；修复 Git 采集，按流程接入 Emby 和 Navidrome 服务活动 | 范围清单中的来源完成采集、加工、展示、运维验收，形成可复用接入模板 | 不以“后续分析需要”为由跳过加工或展示，不把已列入范围的来源悄悄后移 |
| 三 增量产品开发 | 记忆调优与个人基线、长期分析、目标与反馈、Memos 快捷写入等 | 每个产品使用已验收的数据能力，独立完成交互与业务验收 | 可以在本阶段内按依赖并行，不反向改写原始来源事实 |
| 四 标准能力对外提供 | 整理后的查询、产品能力 API、MCP、变更接口及 MCP Events | 消费者真实读取、分页、刷新、纠正和通知链路通过验收 | 不在前两阶段提前建设新增 Bot 接入或公开能力目录 |

现有 HTTP、MCP、事件、日报 cron 和各来源服务继续运行。第一、二阶段可以新增或调整服务客户端所必需的内部读取接口；这属于完成采集侧展示，不等于提前启动第四阶段的标准对外能力建设。

以上是执行门槛，不只是建议排序。产品架构可以在本文保留远期边界，但其代码开发、模型任务与新调度不作为采集阶段的并行工作。已有采集故障修复可持续进行，不必等待文档或加工框架完成。

## 2 现状与问题定位

当前已有来源身份、版本、水位、附件、删除墓碑、PostgreSQL 归档、展示索引、客户端详情和只读 MCP。这些是需要复用的基础，不能据此判定信息已经适合阅读。

现有展示服务仍以来源记录和有限长度标题、预览为主要组织方式；客户端部分详情还需要从原始或规范化载荷中识别正文。虽然已有录音、健康等专用能力，但整体上仍缺少贯穿各类来源的加工结果和阅读契约。见[展示服务](../src/personal_data_hub/display.py)与[详情阅读](../apps/mac-client/Sources/PersonalDataHub/ReadableDetail.swift)。

本轮首先处理三个问题：

1. **信息单位不适合阅读。** 消息、采样点、同步快照和运行日志直接形成列表，用户需要自己还原会话、活动和正文。
2. **内容没有按类型加工到位。** 清洗、分段、去重、附件关联、主题提炼、汇总和时间组织缺少统一交付要求；截取前几百字不等于摘要。
3. **来源接入只完成了部分链路。** 采集成功不保证加工成功，加工结果也不保证客户端已接入合适控件；新增来源容易再次以 RAW DATA 结束。

对应的修复顺序是先把现有数据做出可读结果，再从实际链路固化规范。第一阶段只定义加工所需的最小约定，不先设计目标、建议、长期记忆等全部产品模型。

## 3 总体架构与责任归属

### 3.1 当前必须完成的采集侧

采集侧的完整链路为：**来源接入 → 原始归档 → 类型化加工 → 整理结果与索引 → 内部读取 → 客户端阅读 → 持续更新与对账。**

| 组成 | 责任 | 主要产物 |
| --- | --- | --- |
| 来源适配与设备 Agent | 读取授权范围内的数据，保证身份、增量、时间及交付正确 | 带来源身份和版本的记录、附件、覆盖与删除信号 |
| 原始归档 | 忠实保存原件和来源版本，提供重放基础 | 原始记录、规范化基础字段、附件及提交回执 |
| 加工器 | 将来源载荷转换为可阅读、可查询的信息单位 | 正文、会话、活动片段、录音阅读包、指标序列等 |
| 加工结果存储与索引 | 保存加工版本、依赖、全文索引和有界聚合结果 | 可读对象、检索结果、来源到结果的映射 |
| 内部查询服务 | 为客户端读取一致的列表、详情、分组、搜索与依据 | 稳定的阅读模型，不把清洗责任交给前端 |
| 客户端阅读 | 按内容类型展示，提供展开、检索、原件及异常状态 | 用户能直接使用的来源页面和综合浏览入口 |
| 运行管理 | 分别观察采集与加工状态，处理重试、重建和补漏 | 运行记录、水位、覆盖、积压与恢复入口 |

采集器与加工器分离，仍属于当前核心工作的同一交付范围。采集器不等待模型处理即可提交归档；加工器失败可以重试，不使已经取得的原件丢失。

### 3.2 后续增量产品与对外层

| 后续模块 | 消费的基础能力 | 新增职责 |
| --- | --- | --- |
| 记忆与个人基线 | 可读内容、已有 Mem0 记录、已确认用户输入、指标 | 事实提取、时效、冲突处理、长期记忆检索和更新 |
| 分析建议 | 整理后的事实、指标、记忆及既有反馈 | 周期比较、解释假设、建议、执行与效果复查 |
| 目标与其他应用 | 事实查询及相应业务输入 | 目标、行动、开放事项、知识回顾等产品状态 |
| Memos 快捷写入 | 已可阅读的笔记及稳定来源身份 | 快捷记录、草稿、源端写入与即时回显 |
| 标准对外能力 | 已稳定的整理查询和产品查询 | API、MCP、变化游标、事件发布和消费者适配 |

复用现有仓库、PostgreSQL、附件存储、认证及运行设施。首先按代码和数据所有权划分模块，不为每个模块创建服务或数据库。现有独立处理环境和运行身份保持，源码、部署、数据继续分离。

## 4 第一阶段 原始信息加工与可读展示

### 4.1 加工链路

每类来源从真实样本出发，明确输入、处理规则、输出和阅读方式。完整过程包括：

1. **识别内容。** 区分用户内容、来源摘要、模型产物、附件、同步包和诊断记录；识别真实发生时间、账户、设备和业务对象。
2. **清洗并还原正文。** 处理编码、结构化字段、HTML、转义、重复引用及多段正文，组织附件。清洗不修改归档原件，不丢弃有意义的内容。
3. **还原合适的信息单位。** 消息组成会话，采样点组成指标序列，活动片段组成有覆盖说明的时段，同一录音的产物组成一个阅读入口。
4. **整理与汇总。** 本轮规则负责确定性归并和计算，优先复用可靠的已有上游结果。新增微信主题、要点和长会话摘要的模型生成属于后续分析设计。
5. **生成类型化阅读对象。** 形成标题、内容结构、时间、关键字段、附件、详情和依据入口。列表预览与完整正文分开。
6. **建立索引并接入控件。** 列表、详情、搜索和必要的图表使用同一加工结果。客户端不重复解析各种来源 JSON。
7. **跟踪变化并验收。** 新增、编辑、删除、迟到数据、加工失败和重建都能反映到阅读结果中。

模型摘要属于当前信息加工能力，不必等到分析模块。它回答“这份内容在说什么”，保留原文和依据；“这说明用户有什么长期问题、应该采取什么行动”属于后续分析。加工不以获得用户画像为前提。

### 4.2 现有来源加工清单

以下是目标输出要求，具体字段以来源实际可提供的内容为准。现有实现逐项映射并复用，不重复建设已经合格的处理。

| 来源或内容 | 原始信息需要的加工 | 用户应读到什么 | 关键阅读能力 |
| --- | --- | --- | --- |
| 微信与 CRM 交流 | 解析消息类型、保留发送者和方向、关联媒体、按对象与时段归组；按时间分段；模型提炼暂缓 | 有人物、时间和上下文的会话，而非一长串相同的“交流记录” | 会话展开、原消息定位、媒体显示、正文搜索 |
| Mac 电脑活动 | 对齐原始片段与已有 10 分钟、6 小时摘要，排除重复覆盖；按可靠时间组织活动 | 分时段的活动内容、应用或主题、明确缺口 | 时段折叠、活动详情、来源摘要与原始依据切换；不从摘要长度猜时长 |
| Plaud | 复用转录与融合处理，关联同一录音的音频、文字稿、摘要、章节及处理状态 | 一个完整录音阅读入口，摘要到正文再到音频 | 章节、文字稿、播放、原文定位；来源没有时间戳时不伪造跳转 |
| Memos | 还原 Markdown、标签、附件和关系，区分笔记、日报、周报等内容类型 | 可连续阅读的笔记或完整日报 | 正文排版、附件、关联笔记、全文搜索 |
| 日报 cron 的用户输入与产物 | 定位现有回答、确认内容和报告；保留原话与整理文本的区别 | 可阅读的日记录、用户反馈及来源关系 | 按日期阅读与检索；不新增问卷，不把模型转述标成用户原话 |
| Hermes 执行报告 | 分离业务报告正文、执行结果与诊断日志 | 业务产物作为正文，运行日志进入状态详情 | 报告阅读、原产物入口、失败原因；不把“任务成功”当日报内容 |
| Mem0 | 规范已有记忆文本、来源与时间，保留实际可用的决定和产物引用 | 可读、可搜索且能辨认来源的既有记忆 | 文本阅读、出处、时间、重复或来源不明提示；此阶段不新增记忆写入策略 |
| 邮件 | 解析 MIME/HTML、关联附件；可靠时按邮件身份和引用关系串联，重复引用折叠 | 发件人、主题、往来上下文与正文 | 安全正文显示、会话展开、附件；缺少会话字段时保留单封邮件 |
| 日历与任务 | 统一时间、全天和重复事件、任务清单与当前状态；计划和实际活动分开 | 可读日程与任务列表 | 日期与状态筛选、原对象入口；当前快照不能冒充完整历史 |
| 健康 | 去重、单位转换、累计值与区间处理，按指标定义聚合 | 有日期、单位、覆盖说明的指标及变化 | 图表、样本组成、缺失说明；不展示同步载荷列表作为主要页面 |
| 财务 | 金额、币种、类别、转账、待确认及无效数据统一处理 | 明细账与按周期、类别的明确汇总 | 分类浏览、账单详情、汇总下钻；不合并不同币种 |
| Git 代码活动 | 核查实际已取得的数据，按仓库、时间与对象组织，连接来源链接 | 可读提交与协作记录，准确表达采集覆盖 | 仓库分组、提交主题、原始链接；故障单独显示，不解释成没有活动 |
| Token 与网络用量 | 累计去重、设备与来源范围划分、时间对齐及缺口呈现 | 分设备、模型或网络维度的用量与组成 | 趋势、组成明细、覆盖；不把流量直接当使用时间 |
| 旧证据和历史产物 | 保留原出处及历史格式，按可识别类型接入对应阅读模型 | 可查阅的历史内容 | 正文、日期、历史来源标识；不可解析内容明确归档状态 |

上述清单要落实到实际 `source + kind` 清单。辅助记录，如水位、处理状态和无效片段，不必各自变成动态卡片，但必须在相应内容或来源状态中可查。任何用户内容类型都需要明确阅读处理方式，不以通用 JSON 兜底作为验收。

### 4.3 最小加工结果契约

只先统一加工和阅读需要的公共字段，正文采用有类型的结构：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 稳定加工对象 ID、来源、账户、内容类型及输入记录引用 |
| 时间 | 发生时间或区间、来源更新时间、加工时间、业务时区、未知标记 |
| 阅读内容 | 有意义的标题、可选摘要、类型化正文、关键字段、附件及原件入口 |
| 来源链 | 输入记录 ID 与版本、来源摘要或模型生成标记、加工规则版本 |
| 质量与状态 | 覆盖、缺失、截断、处理结果、过期与失败说明 |
| 查询 | 用于搜索和筛选的正文、日期、对象及类型字段，稳定排序和分页 |

会话、录音、笔记、活动、指标、账单等使用各自的正文 schema，共享身份、时间与来源链。前端消费这些类型，不通过猜测任意 JSON 字段来决定页面。

列表允许短预览，但必须给出完整内容的读取入口；摘要不能覆盖正文。实体关联先使用现有稳定 ID 和有依据的映射，不把完整人物或项目知识图谱作为加工前置条件。

### 4.4 客户端阅读现在完成

本阶段改造已有列表、详情、时间线、搜索和数据图表，交付合适的内容控件。正文的分段、标题层级、会话归组、时间标识、附件与原件入口均属于当前功能验收，不留到 Figma 阶段。

- 首屏回答这是什么、何时发生、主要内容是什么，避免技术字段占据阅读主体。
- 长内容能展开、分页或连续阅读，用户不必导出 JSON 才能获得完整信息。
- 搜索覆盖已加工正文，结果显示匹配片段并定位到内容；中文检索用真实样本验证。
- 图表和汇总可下钻到组成记录，缺失、零值、迟到和历史值分别呈现。
- 采集成功但加工中、加工失败、摘要过期等状态单独显示；能读取的原文继续可用。
- 技术诊断信息放在次级入口，但不能隐藏影响理解的数据缺口。

### 4.5 第一阶段验收门槛

为每种内容类型建立脱敏或私有受控的代表样本，覆盖普通、长内容、附件、重复、更新、缺失和失败等适用场景。验收时同时检查原件、加工结果与客户端实际呈现。

用户应能完成：找到一段内容、直接读懂、展开细节、搜索正文、回到依据，并辨认信息是否完整和最新。规则输出和数值可自动校验；模型提炼还需抽查忠实度与遗漏。源码存在、接口返回 200、截图中出现卡片，都不能代替阅读验收。

本阶段交付逐来源加工与展示矩阵，列明完成、失败和阻塞项。现有来源中的缺项继续属于采集侧待办，不改名为后续产品增强来绕过验收。

## 5 第二阶段 固定接入流程并补齐采集侧

### 5.1 新来源接入流程

从第一阶段实际通过验收的来源提炼标准。后续每个来源都按下表提交完整交付，不允许只新增一个 collector 就登记为接入完成。

| 步骤 | 需要确定或实现 | 必须留下的产物 |
| --- | --- | --- |
| 1 确定范围 | 采什么、不采什么、账户与设备、历史窗口、数据粒度、授权及删除能力 | 来源说明与范围清单 |
| 2 查看真实样本 | 正常、长内容、附件、异常、重复、更新与缺失；确认时间和身份含义 | 受控样本集、字段映射、不可取得的信息说明 |
| 3 定义用户阅读结果 | 用户最终读什么；选用已有内容类型，确需扩展时说明原因 | 原件到阅读结果的映射与验收样例 |
| 4 实现采集与归档 | 复用 Record/Batch、来源 ID、水位、附件和提交回执 | 采集适配及重复、增量、异常交付验证 |
| 5 实现加工 | 清洗、聚合、提炼、来源链、加工版本、索引与失败恢复 | 可重建加工器及质量检查 |
| 6 接入客户端 | 列表、详情、搜索、适用的图表和状态 | 可操作的阅读入口；优先复用已有控件 |
| 7 验证生命周期 | 编辑、删除、迟到补采、分页、失败重试和历史回填 | 完整链路验收记录 |
| 8 接入日常运行 | 调度、来源锁、采集和加工水位、错误定位、补漏 | 运行配置、恢复方法及验收后的就绪状态 |

处理结果也应通过注册信息选择加工器、输出类型和阅读控件，不在多个文件中不断增加互不关联的来源分支。首版采用代码注册和受版本管理的配置即可，不先开发可视化插件市场或通用工作流编辑器。

### 5.2 来源就绪状态

至少区分：已注册、可采集、已归档、已加工、可展示、已验收，以及各环节失败和过期。状态来自实际记录，不把一轮采集成功自动升级成来源已完成。

采集提交水位与加工水位分开；来源健康显示最近采集成功、最近加工成功、积压和覆盖。任务重试使用来源身份与输入版本，不制造重复内容。源 schema 变化时隔离受影响类型并报告，不静默生成空正文后标记成功。

### 5.3 采集侧本轮补齐范围

| 工作项 | 范围与原则 | 完成标准 |
| --- | --- | --- |
| 现有来源收尾 | 第一阶段发现的采集、内容和生命周期缺口 | 逐来源矩阵中的必要项关闭 |
| Git 采集修复 | 修复当前插件问题，核实已有 API 的 commit、PR 等实际能力 | 真实活动可采集、加工、阅读；未覆盖的类型明确记录，不能伪报完整 |
| 手机活动（分析完成后） | 客户端兼任采集任务，复用身份、提交和加工契约；按实际手机平台验证后台能力 | 来源覆盖、离线交付、加工和阅读完整；保留平台限制 |
| NAS 重点服务活动 | 统一来源类别，按阅读、媒体库、音乐库等选定服务建立业务适配 | 展示真实阅读或播放等活动，具备账户与内容身份、去重和覆盖说明 |
| 日报与 Mem0 现有内容 | 读取已采集的主观输入、反馈、决定和产物，补足可读组织和出处 | 内容可阅读、检索、追溯；不要求重新填写，不启动新分析或记忆写入流程 |

2026-10-11 用户明确调整范围：手机采集在分析模块完成后作为增量功能开发，不纳入当前采集侧验收；NAS 首批为 Emby 和 Navidrome。其他来源范围变更仍须明确记录，不把“未来所有可能来源”纳入无限验收范围。

主观精力、情绪、压力、特殊情况及建议执行反馈已由日报 cron 采集。休息、运动、咖啡因、出差等仅使用已有自动数据或用户自然提及的内容，不新增琐碎手工记录，不破坏轻量日报原则。

### 5.4 采集侧总验收

阶段一和二共同通过后，才进入阶段三：

1. 已确定范围内的来源都有数据范围、类型清单、加工方案和实际阅读结果。
2. 当前用户内容不再以 RAW DATA 列表或通用字段堆积作为主要浏览方式。
3. 新来源可依照标准流程接入，采集、加工和展示的责任方明确。
4. 历史与增量采用同一加工语义；重跑、更新和删除不会留下仍被正常读取的错误结果。
5. 有采集与加工分别可查的状态、积压、缺口、重试及恢复入口。
6. 阻塞项有明确记录；无法完成的范围需要明确调整决定，不能静默宣布采集侧完成。

这是一道交付门槛。保留后续产品方案不代表可以绕过门槛并行实施。

## 6 加工存储与运行设计

### 6.1 保留原件 加工结果可重建

复用已有 PostgreSQL 和附件存储，在归档之外保存类型化加工结果、依赖映射、索引及处理状态。加工器拥有其输出结构；前端不直接承担来源适配。现有 display_index 按能力演进，不能让它继续同时承担完整正文、模型产物和所有业务状态。

加工 ID 与来源引用稳定，记录输入版本、规则版本及模型运行信息。不同来源描述同一事件时可以建立关联，但保留原件，身份相同、内容重复和事件相同分别判断。人工纠正单独保存，重建继续应用。

源更新后只失效受影响结果，按记录或时间窗口重算。源删除继续遵循现有归档语义，并传播到正文、索引、摘要和相关聚合；派生结果的历史版本不能成为被删除正文的保留后门。

### 6.2 规则处理与模型加工

时间转换、精确去重、累计处理、数值汇总和字段校验由确定性代码负责。内容提炼、主题及长文本摘要可使用已有模型设施，以内容类型配置处理策略。短笔记无需强制再摘要，高频重复来源不逐条调用模型，已合格的上游摘要不重复生成。

模型输出保留来源引用、处理版本和状态；失败不丢原文。可读原文作为降级入口，但当前必须完成会话归组与完整阅读，微信长文提炼不属于当前验收要求。

以实际样本评估遗漏、错误归因和过度压缩；预算、批次、缓存和增量触发按来源设定。加工成本不由客户端刷新触发，页面请求只读已有结果。

### 6.3 日常运行与回填

复用既有调度和来源锁。归档提交后持久记录需要加工的输入版本，后台恢复未完成任务；加工结果和索引提交成功后才推进加工水位。

回填与日常增量使用同一加工器，按优先级和限流避免长历史任务拖慢当前数据。先用代表样本验证，再处理用户当前浏览窗口，随后完成本轮历史范围。按来源重建，不默认重算全部资料。

记录采集量、加工成功与失败、积压、更新延迟、模型开销和客户端读取耗时。性能门槛根据真实规模测量后确定。原始归档、人工修正、配置和数据卷保持既有归属，不在源码目录存放生产载荷或凭据。

## 7 第三阶段 增量产品架构

以下模块在采集侧总验收后启动。其输入是已经可读、可检索、可追溯的数据，不再各自直接处理一遍 RAW DATA。

### 7.1 记忆 个人基线与当前状态

复用既有 Mem0，新增事实分类、有效期、冲突处理、确认与同步策略。既有 AI 会话决定和产物优先从 Mem0 消费，只有发现具体缺口才评估额外采集。

确认基线保存身份、偏好、长期约束与主线方向；统计基线由统一指标计算；当前状态组合近期变化、活跃事项与有效约束。三者分别更新，不把一次情绪或活动直接固化为长期特征。

Hub 保存新记忆的依据、候选状态和外部 ID 映射，Mem0 承担检索与共享。来源不足的旧记忆标明不可追溯，不补造证据。识别自身摘要被重新采集的情况，防止报告和记忆循环提炼、重复计为独立证据。

### 7.2 分析 建议与反馈

微信会话主题、要点与摘要提炼纳入此模块的后续目标。开发分析模块时统一确定它的用途、材料范围、与记忆及状态分析的关系、交互和成本；旧 grok 配置、阈值、窗口及读取接口均不是已经冻结的设计。当前后台执行和新任务生成关闭，既有数据保留。

复用 Hermes 日报 cron 的轻量交互和已有反馈，不新增重复问卷。分析先冻结材料并读取统一指标，再生成观察、解释假设和建议；保留依据、覆盖、规则及模型版本。

目标、建议、执行和效果分别建模。用户是否接受、是否执行、执行难度及是否有帮助不是同一个“完成”状态。周期复查消费已有反馈，允许用户纠正解释和改变目标。个人状态分析可优先实施，但系统结构支持目标推进、工作复盘及其他应用。

旧账本与原始回答继续保留原归属。新应用通过兼容适配取得回答、确认和回执；按业务类别切换唯一写入者，避免新旧 cron 同时写入 Memos、Mem0 或任务服务。原始用户内容和模型解释分开保存。

### 7.3 Memos 与其他客户端应用

Memos 阅读已在采集阶段完成；快捷键写入、草稿恢复、编辑和目标关联在本阶段作为增量应用实现。写入源端取得正式 ID 后即时展示，归档状态独立跟踪；超时先核对结果，不盲目重发。模型摘要不覆盖笔记原文。

其他新增页面围绕各自产品对象建设，复用已有阅读控件、全文检索、图表和原件入口。Figma 统一视觉样式在功能和交互稳定后完成；采集阶段的可读性验收不以等待 Figma 为理由推迟。

## 8 第四阶段 标准 API MCP 与事件

待整理和产品能力稳定后，才定义对外能力目录、接口与 MCP 工具。内部查询服务被复用，HTTP 与 MCP 不再各算指标或重新处理原始信息。

| 对外能力 | 提供内容 |
| --- | --- |
| 整理后信息查询 | 可读内容、活动、时间线、搜索及原件依据 |
| 指标查询 | 统一口径数值、覆盖、组成及计算版本 |
| 个人上下文 | 与问题相关的确认事实、当前状态、记忆和约束 |
| 产品查询 | 已验收产品的目标、回顾、建议与结果 |
| 变化读取 | 指定游标后的新增、更新、纠正、替代与撤回 |

结果包含稳定 ID、版本、数据截止时间、覆盖说明、来源引用及分页。按调用者可见范围返回，摘要和聚合也继承相应限制。保留现有认证身份、密钥及旧工具兼容；新增写入能力独立限定命令范围，不开放任意原始归档修改。

MCP Events 发布内容就绪或结果变更，携带对象 ID、版本、变化类型和读取入口；正文按需查询。复用持久投递、去重和重试，区分回调接收、正文读取、消费者处理和用户通知。内部加工任务事件不自动变成面向 Bot 的通知。

dot、Grok Bots、Hermes 分别适配实际支持的认证和触发方式。MCP 查询可用不代表消费者支持相同事件协议；不支持原生事件时再评估轮询或其他既有触发方式。真实验收需要消费者读到指定版本，并能处理更正和撤回。

已有 Grok CPA 文本代理与云端 Bot 的原生连接能力分别判断。该验证属于本阶段，不是采集侧加工或新来源接入的前置工作。外部聊天已经保存的副本不能承诺自动清除，可通过后续纠正通知更新。

## 9 分阶段工作包与并行边界

### 9.1 第一阶段工作包

| 编号 | 职责与所有权 | 输出与依赖 |
| --- | --- | --- |
| P0 来源与阅读盘点 | 逐 source/kind 样本、现状、预期阅读结果及问题清单 | 先确定加工验收样例，不设计全部未来产品 schema |
| P1 加工公共底座 | 最小阅读契约、加工注册、结果存储、输入版本、状态、失效和内部读取 | 从 P0 的真实类型落地；协调公共模型和迁移 |
| P2 会话与文本加工 | 微信、邮件、Memos、日报、Hermes、Mem0 的正文和分组 | 使用 P1，附类型化结果与对应阅读验收样例 |
| P3 活动与录音加工 | Mac 活动、Plaud 与现有处理器衔接 | 使用 P1，复用现有转录和摘要，补组织与来源链 |
| P4 结构化数据加工 | 健康、财务、日历任务、Git 已有数据、Token 和网络 | 使用 P1，统一规则、指标、明细和覆盖 |
| P5 客户端阅读改造 | 按内容类型实现列表、详情、搜索、图表和状态 | 与 P2/P3/P4 按类型共同交付，不等后续产品阶段 |
| P6 采集侧集成验收 | 回填、增量、修改删除、处理失败、检索及客户端实际阅读 | 汇总来源矩阵；不以单模块测试代替阅读链路验收 |

P0 先确定首批样例与最小约定，P1 按此落地；不同来源的加工与对应控件随后可以并行。P1 不演变成长期的平台重构前置。P2、P3、P4 不同时修改统一大文件：各自提供独立加工模块，由集成负责人注册装配。P5 统一管理客户端入口，共享控件的文件归属提前分配。

### 9.2 第二阶段工作包

| 编号 | 职责 | 完成标准 |
| --- | --- | --- |
| S1 接入规范与模板 | 将已验收链路固定为来源说明、采集适配、加工、阅读和运行模板 | 新来源能逐项遵循，不遗漏加工与展示 |
| S2 Git 故障修复与范围核对 | 修复既有来源，核对实际事件类型及历史覆盖 | 可信活动进入同一加工和阅读链路；故障修复本身可提前进行 |
| 后续 手机客户端采集 | 分析模块完成后确定平台，完成采集、交付、活动加工及阅读 | 不阻塞本轮采集；平台后台和权限限制真实验证，身份和水位稳定 |
| S4 NAS 服务活动 | 确定首批服务，按业务语义实现适配、加工和展示 | 每个服务通过完整接入流程 |
| S5 总验收与收尾 | 关闭本轮来源清单缺项，核对长期运行和恢复 | 达到第 5.4 节门槛，记录采集侧实际完成状态 |

S2/S3/S4 在规范固定后可并行。第一阶段暴露的既有采集故障可立即修复；新来源的完整开发不抢在现有原始信息加工和流程固化之前展开。

### 9.3 后续阶段工作包

第三阶段再拆记忆与基线、分析建议、目标反馈、Memos 快捷写入及其他应用，各自声明输入的数据能力和验收场景。第四阶段再拆标准能力目录、HTTP/MCP 适配、事件与 Bot 消费者。

不沿用“公共契约一完成就并行启动记忆、分析、快捷写入和 Bot 接入”的排期。阶段内可并行，阶段门槛不能被 worktree 并行绕过。

### 9.4 文件与数据所有权

当前建议新增来源加工模块及查询模型，沿用既有结构逐步分离；不先创建全部未来模块的空目录。`contracts.py`、`storage.py`、`server.py`、`cli.py` 和迁移装配由 P1/集成负责人协调。加工器与客户端子组件由相应工作包拥有。

每个 fork 明确负责文件、输入输出、真实样例、测试与验收、非目标。测试与回填验证使用隔离数据，不能多个 worktree 同时迁移生产库或注册重复调度。生产身份、密钥、卷和来源水位保留。

## 10 可行性与风险处理

| 范围 | 可行性判断 | 主要风险与应对 |
| --- | --- | --- |
| 类型化信息加工 | 有原件、展示索引和部分处理器可复用，可增量完成 | 先用真实样本明确业务单位，避免只有统一字段没有真实内容组织 |
| 客户端可读展示 | 现有原生客户端可改造 | 按内容类型交付实际控件，不能仅改标题、配色或 JSON 格式 |
| 微信模型提炼 | 已暂停，后续分析模块统一设计 | 不阻塞当前采集；旧代码、参数及接口仅供参考 |
| 接入流程固化 | 由已完成链路提炼，技术风险较低 | 接入验收必须覆盖加工和阅读，防止只以采集运行成功结案 |
| Git 来源修复 | 可单独定位，但具体根因与覆盖待来源任务核实 | 不根据接口存在宣称已取得 PR 等全部内容 |
| 手机活动 | 方向可行，能力取决于目标平台 | 分析完成后验证权限、后台限制和数据粒度；不作为本轮采集门槛 |
| NAS 服务活动 | 按重点服务逐项接入可行 | 优先业务历史/API；系统日志不能替代真实用户活动 |
| 后续记忆与分析 | 能复用采集加工成果，效果需产品阶段验证 | 不能为提前跑分析而绕过采集侧质量门槛 |
| 对外 MCP 与事件 | 已有服务端基础可复用，消费者存在差异 | 最后依据稳定能力封装，分别验收查询、刷新和主动通知 |

关键边界是来源粒度与真实性：没有真实起止时间就不声称精确活动时长，没有原始回答就不声称用户直接表达，没有可靠删除信号就不根据窗口缺失删除。具体缺口在来源矩阵体现，不用模型补造。

当前交付物是架构与开发指引。后续第一项实施任务应从 P0 的现有来源阅读样例与 P1 的最小加工链路开始，交付第一类真实数据的加工和客户端阅读结果，再按类型完成全部本轮现有来源。
