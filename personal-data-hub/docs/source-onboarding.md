# 数据源接入流程

2026-10-13 当前处于[性能止血](performance-relief-20261013.md)阶段：宿主轮询调度器已停止并禁用，后台加工与自动回填关闭，CRM 全量核对暂停。推送及显式提交仍可归档入队，但本流程不自动恢复轮询、加工或历史扫描。

实施版 1，依据 M1–M4 已落地的代码整理。服务端负责采集、加工和内部读取；Mac 负责控件。新增来源先完成开发，再在收口阶段做一轮简单验收。

## 1 先确定实际能读到什么

记录服务实例、账户和允许读取的范围，再确认源端接口/表和稳定身份。优先复用已有只读接口及凭据；需要读本地 SQLite 时使用 `collectors.snapshot()` 的 backup 快照，包含 WAL，不修改业务库。

区分事件、可变对象、累计快照、当前状态与上游模型产物。源端只有快照就叫快照；没有实际开始/结束、阅读时长或用户原话就不补造。先填 [来源模板](templates/source-processing-profile.md) 的范围与字段，再写适配器。

## 2 归档契约

使用现有 `Record / Batch`，在 `runner.adapter()` 注册适配器，配置放在已有私有 Hub 配置中。库、数据卷、身份和鉴权不随来源接入迁移。

| 字段 | 接入规则 |
| --- | --- |
| source / account | 每个实例与账户固定身份，不按展示名混合账户 |
| external_id | 源端 ID 或明确的组合键；同一个对象更新仍用同一 ID，重复播放不能仅用歌曲/影片 ID |
| kind | 声明本轮业务类型；新增类型同时提供加工规则，不自动当作通用 JSON |
| raw | 实际采集的业务字段；可保存明确声明的源端投影，不归档请求凭据或认证头 |
| normalized | 来源专有的已知字段、时间含义、内容范围和质量标记；不塞入推测结论 |
| occurred_at | 源端发生/报告时间；观察快照没有发生时间则保持空，另写 observed_at |
| updated_at / timezone | 真实源端更新时间及其时区；未知时区不改写成确定的 UTC 业务日 |
| assets | 沿用现有附件归档与读取；来源正文和附件完整程度分别说明 |

增量水位在归档成功后由现有 runner 提交。固定本轮查询上界，保存推进后的水位；需要回看就写明回看长度。分页必须完成；部分入库后失败可以通过稳定身份重跑。只有真正完整、同一范围的清单才能 authoritative；近期窗口和当前播放均不能推断删除。

## 3 从归档变成阅读对象

在 `processing/` 增加来源规则，并登记到 `registry.PROFILES`，确认它被当前采集侧使用的 `COLLECTION_PROFILES` 纳入；后者由注册表自动筛选。微信提炼属于暂停的分析规则，只保留在历史注册表，不恢复采集侧路由。复用现有队列、发布、全文分块和证据机制，不另外建一套加工调度。

| 实际扩展点 | 用途 |
| --- | --- |
| PROCESSOR / PROFILE_VERSION / KINDS | 固定规则身份、版本和匹配类型 |
| accepts(record) | 精确匹配本规则适用的源记录 |
| header(record, scope) | 处理中对象的 type / variant |
| scope(record) 或 scopes(record) | 聚合身份；一个健康快照可以对应多个业务日 |
| process(rows) 或 process_scope(rows, scope) | 输出 ProcessedContent；空成员由共用 Worker 撤下对象 |
| dependency_ids(rows) | 需要冻结的已归档关联输入，如转录对应的音频记录 |
| reading.text_blocks / fields_block / ref | 完整正文分块、字段投影、record_id/hash 引用 |

对象按 processor/source/scope 生成稳定 ID。规则改变时升级 PROFILE_VERSION，用现有 rebuild-content 扫描重建；更新和删除沿用归档事务内的钩子。每个新类型都说明原文、确定性投影或上游摘要的来源；本轮加工只做确定性整理和来源既有产物适配；新增模型提炼留到后续分析模块统一设计。

无法支持的 kind 留在 processing/status 的 unsupported 清单；技术产物可以有明确的辅助归档策略，但不能算成已加工的业务正文。不要让客户端自行猜 raw 字段。

## 4 交付内部读取与 Mac 需求

沿用 contents 列表、详情、blocks、evidence 和 processing/status，保持 schema/revision 分页规则。列表不装载整份原件，详情返回类型字段，长正文和组成通过块分页读取。需要兼容旧页面时只扩已有 display 映射。

接口与控件说明保存在 `docs/client-requirements/` 供用户后续接入参考，不要求 Mac 随服务端每个节点同步开发。只有 Mac 采集端缺少必要输入或能力、实际阻塞服务端时，才提出当前开发需求。客户端由用户在 Mac 实现，接入时间由用户安排。标准对外 MCP 和 Bot 事件在采集链路完成之后再做，本轮不注册新外部工具。

## 5 上线和历史补采

沿用宿主采集服务及正式 mcp/crm 部署。私有配置只新增受影响来源；需要重启就只更新受影响服务，保留设备、OAuth、密钥及卷。已知来源允许从已有历史补采；只支持当前状态的来源不伪造历史。

正文检索使用既有 PostgreSQL 的 `pg_trgm` 与 `ix_hub_content_search_trgm`，阅读排序使用 `ix_hub_content_reading_order`。已有大库升级先并发补建索引，再发布代码，避免在采集写入锁内进行整库索引构建；新空库由加工迁移初始化。没有新建数据库或检索服务。索引有效不代表真实搜索性能已经验收，当前结果见 [M5](collection-m5-validation.md)。

普通轮询来源默认每 6 小时同步一次，每日约 4 次；加工队列也按 6 小时开启批次，批次内处理完已有任务再休眠。Emby 只能读取当前播放会话，保留 60 秒观察采样，加工和对外读取按同一批次节奏组织；推送来源的接收入口保留。

日常调度默认不巡检全量历史。新增规则或补历史时显式执行 `rebuild-content --source SOURCE --processor PROCESSOR`；需要完整重算使用 `--force`。既有 `--background-page` 可以手工逐批恢复内部位置，规则版本没变且加工关系已存在时只读取 ID、类型和规则版本，不重新加载完整 JSON；版本变化或 force 仍核对原件。各来源的采集水位与这个内部回填位置分开。

周期拉取遇到完全相同的记录时只计入 duplicates，不重写归档和展示索引；来源检查成功时间取 `last_run.ended_at`。记录的 `observed_at` 保留最近一次归档或变更观察时间。显式 HTTP/设备推送仍可刷新逐条观察时间，真实新观察应使用稳定而独立的事件身份，不能靠反复同步旧记录制造新活动。

调度父进程初始化数据库一次，子任务使用 `--skip-schema-init`，不重复检查表和迁移。手工独立 CLI 仍默认执行初始化。

归档成功、阅读就绪、来源检查成功是三个不同状态。来源说明必须给出历史范围、采样/上报缺口及仍未完成的客户端部分。上线登记代码与镜像版本；不把后台入队或空结果称为整条链路验收通过。

## 6 最后一轮简单验收

采集侧开发完成后统一看：新数据能归档并读全；正文中段可搜索；一个更新和删除能反映到阅读层；数值与源端含义一致。Mac 控件的实际阅读体验另行验收，不作为服务端验证或后续模块的前置条件。只检查本轮适用路径，不在每个节点重复跑整套测试。

当前实例说明放在 `docs/sources/`；实施记录和客户端交付分别登记，不要求用户重复填写已经由源码、配置和来源核对确定的事实。
