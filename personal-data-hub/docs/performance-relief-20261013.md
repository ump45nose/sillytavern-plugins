# 2026-10-13 性能止血

本轮针对用户提供的持续故障链路先恢复入库：CRM 全量核对持有来源锁，后台加工在有积压时绕过 6 小时间隔，发布正文持有全局写锁，慢磁盘与 120 秒超时重做相互放大。本轮不对整机峰值负载作完整归因。

## 已做的调整

- 宿主与容器配置均设置 `processing_enabled=false`、`processing_backfill_on_start=false`、`sources.crm.enabled=false`。保留阅读结果、加工任务、原件、水位和微信提炼暂停配置，不清空队列。CRM 的 enabled 控制定时轮询，不关闭已有微信 webhook。
- 起初将其他轮询的并发从 3 降为 1，但正式检查中空批次入库仍等待 6.5 秒、健康读取超时，因此最终停止并禁用 `personal-data-hub-collectors.service`。所有后台轮询和加工保持暂停，重启不会自动恢复；各来源原配置、节奏与水位保留。周期相同内容不重复更新原件/展示索引的已有优化保留。
- 加工调度在成功、失败和超时后都等待 `processing_interval_seconds`；有积压也不每 5/30 秒继续。当前间隔为 21,600 秒，每个后台阅读 worker 最多处理一个任务。
- 阅读任务租约从 120 秒改为 180 秒，长于后台 worker 的 120 秒上限。未完成任务仍保留；不会因为批次限时与租约相同而恰好在发布时过期。
- PostgreSQL 发布改为在同一连接、同一事务中尝试取得全局写锁；拿不到就归还任务并退出，不等待入库。取得锁后，整个发布事务设 10 秒上限，超时回滚，原件与已有阅读内容保持。代价是重型内容可能无法在本模式下完成加工；当前后台仍保持关闭。
- 保留原件、删除、输入哈希和 generation 的一致性保护，没有移除全局写锁，也没有改共享 PostgreSQL 的全局参数。[事务超时的 PostgreSQL 17 文档](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-TRANSACTION-TIMEOUT)说明了本轮连接内设置的作用。

## 另外发现的启动问题

NAS 重启后 PostgreSQL 在 data_net 中的地址由 `172.22.0.2` 变为 `172.22.0.6`。容器使用原服务名 `postgresql`，宿主两项服务却仍使用旧 IP，并反复启动失败。仅更新宿主 Hub 与 CRM 来源的数据库连接地址，保留数据库、用户和密码，恢复健康 webhook。没有给共享 PostgreSQL 新增端口或重建它。

这个宿主 IP 修正解决当前恢复问题，但不是固定连接地址；容器网络再次重建后仍需核对地址。持久的宿主连接入口另行处理，不把本轮临时地址称为长期网络方案。

## 生效范围与代价

微信、健康、账单及已有设备推送、显式提交继续入库，已有只读入口和已加工结果保持。依赖后台轮询的来源暂不更新；新增推送可以归档，但阅读加工暂不更新。原来的处理错误、积压和历史核对缺口不伪装为已解决。CRM 定时全量核对停止后，不能依赖它补齐其他 CRM 操作的镜像或发现完整清单删除。Emby 的当前会话采样暂停期间会留下观察缺口，不回造历史。

重型加工和正文检索的长期优化还未完成。恢复后台加工之前需要处理大对象和全文索引的写入成本；本轮不会自动重新开启队列或历史扫描。

正式镜像为 `local/personal-data-hub:0.4.9-performance-relief-20261013`，容器 healthy，健康 webhook active；轮询调度器 inactive / disabled。本轮仅重建 crm，1000:1001 身份、密钥、挂载和 data_net 保持；既有 48 容器启动检查无缺失或意外停机。

实现完成后的四项隔离 PostgreSQL 检查通过，耗时 7.35 秒：积压与失败不会绕过间隔；发布让位后可重新领取、超时仅作用于发布事务；编辑和删除仍阻止旧任务回写。没有运行全库测试、大库重建或真实消息回放。

停用全部轮询后，正式 CRM 来源的认证空批次入库返回 200，耗时约 0.007 秒；无新增记录、删除、客户端或水位变更。宿主健康读取返回 200，耗时约 0.083 秒；既有笔记列表此前核对为 200 / 0.517 秒。数据库采样无 advisory lock 等待，既有 source:crm 与全局入库锁可取得；没有 process-pending、rebuild-content 或 CRM 全量 worker。

这些是指定路径的当时结果，不是所有真实推送的性能承诺；原生微信下一条真实消息未回放验收。停止队列后整机仍观察到磁盘等待，因此不能宣布整机负载 239 的完整根因已经查清。
