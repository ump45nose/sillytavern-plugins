## 1 开发目标与边界

### 1.1 完成后的使用结果

- 客户端直接显示笔记、日报、会话、活动、录音及类型化数据；技术记录进入相应状态详情。
- 标题、正文、要点、时间、人物和附件按内容类型组织，完整内容可以展开，搜索可以定位正文。
- 来源原件、上游摘要和 Hub 加工产物有明确区别，数值与摘要均可追溯。
- 编辑、删除、迟到补采、模型失败和重建能反映到内容及索引；采集成功与加工就绪分别呈现。
- 新来源使用同一流程完成归档、加工、阅读控件和运行验收。

执行分工：本对话只实现服务端；每个需客户端配合的节点，交付接口契约、控件需求和验收场景到 `docs/client-requirements/`。客户端由用户在 Mac 实现，接入时间由用户安排。当前不存在 Mac 阻塞；客户端文档仅供后续参考，不作为当前开发要求。服务端独立完成加工、接口、生命周期及末尾的一轮简单验证，可以继续后续服务端模块；Mac 阅读体验单独登记待验收，不因此停下服务端工作。只有确实缺少 Mac 采集端提供的必要输入或能力时，才向用户提出阻塞开发需求。

最终配色、视觉 token 和装饰留给 Figma。分段、信息层级、会话组织、图表下钻和处理状态是本轮必须完成的阅读功能。

### 1.2 继承的范围约束

主观状态和建议反馈复用已有日报 cron 的结果，不增加打卡或琐碎手工记录。Mem0 只加工已有文本、决定、产物及出处，本阶段不生成新长期记忆。Memos 首先完成阅读，快捷写入属于后续应用。

Git 收口和 NAS 重点服务活动进入后续来源补齐阶段，各自须完成加工和展示。2026-10-11 执行时用户明确调整范围：手机采集放到分析模块完成之后，作为增量功能，不阻塞本轮采集侧验收；NAS 首批限定为 Emby 和 Navidrome。

已有只读 MCP、HTTP、事件和日报保持其运行入口。新内部阅读接口仅服务本轮客户端和验证，新增标准对外能力与 Bot 推送在后续阶段实施。

## 2 当前实现与改造落点

以下是代码和现有部署文档反映的基础；来源覆盖、加工忠实度和客户端实际体验仍需在实施时用代表样本验收。

| 位置 | 已有能力或限制 | 本轮改造 |
| --- | --- | --- |
| `contracts.py` 的 Record/Batch | 来源身份、原始/规范化载荷、时间、附件、删除与完整清单 | 保留采集契约，新增独立加工契约，不改原 ID |
| `storage.py` 的 Store.ingest | 内容哈希去重、修订、同事务预览与展示索引 | 对真实变更加入持久加工任务；周期拉取的重复内容不重写原件/索引，显式推送可刷新 observed_at |
| `storage.py` 的 _purge | 删除原件、修订、引用、现有索引并保留墓碑 | 同事务撤下相关加工内容和检索结果，安排剩余内容重算 |
| `hub_display_index` | 每个原始 record_id 对应一行，标题 160 字符、预览 500 字符 | 保留旧索引；新增可表达单记录和多记录对象的加工存储 |
| `display.py` | 概览、指标、按记录时间线；搜索标题和短预览 | 提取共用指标规则；新阅读列表和正文检索读取加工结果 |
| `ReadableDetail.swift`、`Models.swift` | 详情仍解析 raw/normalized、识别正文与来源字段 | 新阅读模型由后台确定，客户端按内容类型解码和渲染 |
| `scheduler.py`、`runner.py` | 独立来源进程、并发上限、超时、退避、来源锁、水位 | 复用现有调度入口，增加有界的加工任务执行通道 |
| `plaud_content.py`、Plaud processors | 分源稿、覆盖校验、日报融合、摘要及处理状态 | 复用产物和任务；阅读适配不重新调用 ASR 或另建摘要生产者 |
| `checks/display-smoke.py` 等 | 日期、去重、缺失、分页、鉴权等合成验证 | 保留既有回归，补阅读契约和加工生命周期验证 |

已有[采集模块增量设计](collection-plan.md)是来源读取与归档专项参考，不能代替本方案的加工和阅读验收。其手机排期、来源分批等尚需按本轮明确范围协调；总体阶段门槛以[全局架构](target-architecture.md)为准。

## 3 阅读对象与加工契约

### 3.1 最小类型集合

| 阅读类型 | 内容单位 | 初始覆盖 |
| --- | --- | --- |
| document | 一篇完整文本及其附件、章节、要点和出处 | Memos、日报、Mem0、Hermes 业务正文、历史报告 |
| conversation | 一个对象在业务日内的会话集合，包含原消息及可选主题段 | 微信；邮件按可靠线程引用另作专用归组 |
| activity | 一个明确时间范围内的活动及覆盖 | Mac 活动与来源摘要，后续手机/NAS 活动 |
| recording | 一份录音的音频、草稿/正式稿、已有摘要与相关日报 | Plaud |
| metric_day | 某指标、业务日期、单位和来源范围的结果与组成 | 健康、财务汇总、Token、网络 |
| structured_record | 有类型的业务对象 | 日历事件、任务、账单、Git 提交、联系人资料 |

同一类型可以有 `variant`，如 `document/daily_review`、`structured_record/bill`，但必须有对应 schema 和控件。同步状态、无效片段、设备配置和处理日志注册为辅助类型，不挤入主时间线；其内容在来源或对应阅读对象的状态中可查。

### 3.2 对象身份与聚合边界

单记录对象使用 `processor_namespace + source + record_id` 作为稳定键，编辑保持对象 ID。聚合对象使用固定 scope：微信首版为账户、来源、person_id、业务日期；指标为定义、来源范围、业务日期与单位；录音为来源和 recording_id。

对象 ID 不由当前标题、消息数量或摘要生成，避免每次重算换 ID。聚合业务时区写入加工配置并保留版本，不能由客户端本次显示时区临时决定。调整分组时区视为明确重建与迁移；显示时区可以不同，页面标明业务日期。

微信首版以日会话对象为稳定入口，内部按时间间隔形成可折叠段，模型主题也只改变内部段落。邮件仅在 Message-ID、References、In-Reply-To 等实际信息足够时归线程，同主题不直接合并。未知时间的内容独立展示，不用 observed_at 假造发生时间。

### 3.3 公共头与正文分块

列表只返回公共头；详情返回类型化元数据与正文分页入口：

| 字段 | 约定 |
| --- | --- |
| `id / type / variant / schema_version` | 稳定对象身份和内容 schema；仅增量兼容的字段变更保持大版本 |
| `revision` | 当前对象已发布内容版本，正文续页与该版本绑定 |
| `source / account / scope_key` | 来源及业务范围，继承现有账户隔离 |
| `occurred_at / interval / business_date / timezone` | 按内容类型使用，未知值保持未知 |
| `title / preview / summary` | 标题有意义；preview 是短摘录，summary 是明确标注的提炼结果 |
| `processing / coverage / warnings` | 必需步骤和增强步骤各自的状态、已知覆盖与缺口 |
| `metadata` | 类型专有字段，如标签、参与人、币种、录音时长、模型产物属性 |
| `content / assets / evidence` | 对应正文、附件与完整依据的读取入口；列表不内嵌大载荷 |

长正文、聊天和转录使用有序块。块支持 Markdown 段、原消息、转录片段和类型化行，包含稳定块键、顺序、文本或专有字段，以及具体的 record_id、输入 hash 和可用原文范围。附件使用现有 asset_id 与鉴权读取；不重复存储音频或文件。

列表摘录有长度限制，正文读取不能静默截断。初始预算建议为每页最多 50 个对象、正文响应不超过 256 KiB 的编码大小；消息超长时分块，返回续页信息。预算在真实样本和客户端验证后冻结，不能把超限内容当作空内容。

### 3.4 成功 失败与降级

每个加工 profile 明确必需步骤和增强步骤。例如 Memos 的原文提取、Markdown 组织、附件关联和检索是必需步骤；短笔记不需要模型摘要。长会话的消息归组是必需步骤，重点提炼是否为必需步骤由其阅读验收要求确定。

保存 `pending / running / ready / partial / failed / stale` 等处理状态，质量警告独立保存。原文可读但必需提炼失败时显示可读降级和失败原因，不能标记全流程完成。某次长文没有摘要不影响已经合格的短笔记阅读。

来源 freshness、加工完成时间、内容发生时间分别展示。周期拉取相同内容只记录来源检查成功时间，不重写逐条 observed_at 或加工 revision；显式推送的观察时间继续保留。不对相同内容重新付费生成模型结果。

## 4 存储 依赖与任务机制

### 4.1 复用原始存储 新增加工存储

拟新增以下四组表，实际 DDL 在底座任务中落实并验证：

| 表 | 核心字段与职责 |
| --- | --- |
| `hub_content_objects` | id、processor、source/account、scope_key、type/variant、schema_version、revision、generation、时间、title/preview/summary、质量状态、类型化元数据；保存已发布阅读对象 |
| `hub_content_blocks` | object_id、revision、block_key、sequence、block_type、类型化内容、可搜索正文；保存长内容和块级原文引用 |
| `hub_content_inputs` | object_id、record_id、input_hash、输入角色；记录完整依赖，不只保存列表显示的少量引用 |
| `hub_processing_jobs` | processor、scope_key、desired_generation、published_generation、profile_version、状态、租约 token/期限、重试时间、次数、错误、路由和运行元数据 |

任务表同时记录每个加工 scope 的持久执行状态，唯一键为 processor 与 scope_key；重复入队合并为更新期望代数。四组表不会替代 `hub_records / hub_revisions / hub_checkpoints / hub_runs`。新表可保存已校验无 NUL 的加工结果，归档原始 JSON 的兼容语义保持。

不创建另一套附件拥有权：加工引用只是导航，原始记录仍决定附件保存与垃圾回收。来源删除时加工入口同时撤下；附件分享给其他原始记录时继续保留。

初版只保留当前可读内容及必要的安全运行元数据。旧加工正文版本不无限保存；被删除内容不得留在旧块、失败缓存、摘要或搜索文本中。人工修正若纳入本轮功能，使用独立持久 override 记录，重建不丢失；首版不以开发完整纠正系统阻塞阅读加工。

### 4.2 变更入队

在 `Store.ingest` 的原事务内，对新记录和真实 hash 变化调用轻量的加工变更钩子；正文清洗、聚合、模型请求都在事务外执行。CRM 使用传入 connection 的路径、HTTP 推送、周期拉取和 CLI 补采都经过该钩子，不能只在 runner 中触发。

路由只使用最小字段和注册规则：记录级对象、已知业务 ID、时间桶。更新跨人物或日期时旧 scope 与新 scope 都入队。新增记录即使尚无依赖行，也会触发所在聚合 scope，避免只根据已存在的 inputs 找不到新成员。

无法解析路由字段时保存诊断并入队来源级核对任务，不能丢弃记录或默认无事可做；来源核对负责将其路由到未知时间或问题内容入口。路由过程中不调用模型或远端 API。数据库无法持久入队属于该次事务提交失败，正常加工失败则不阻塞采集。

重复记录的 observed_at 更新不入队。processor 的规则/profile_version 变化需要显式重建相应 scope，即使源 hash 不变也能升级加工结果。

### 4.3 后台执行与防止旧结果回写

1. Worker 在短事务中领取任务，记录目标 generation、profile_version、lease_token 和租约期限。
2. 在一致的读取窗口中取得输入 ID/hash 清单和必要正文，生成输入 fingerprint；不得持有数据库 writer lock 执行模型。
3. 完成清洗、计算、可选提炼与契约校验，按当前需要将结果准备为有界块。
4. 发布时采用与归档一致的锁顺序：先 writer lock，再相应任务/对象锁；短事务再次校验租约、generation、profile_version、来源存活及输入 hash。
5. 只有仍对应当前输入的结果才能原子替换对象、块和依赖，并推进 published_generation。旧结果丢弃，保留新代任务待执行。
6. 失败保存安全错误与下一次重试；新的输入版本重置该版本的失败状态。超时、进程退出或租约丢失不能将其他活跃 Worker 的任务改成失败。

长模型调用需要租约续期或独立进程监督。模型超时执行有界终止；若无法确认远端计费或成功状态，记录调用状态并核对缓存，不宣称重试可以保证不重复计费。

同一 scope 的新事件可短暂合并后重算，避免每条消息触发模型；归档立即提交。新增或迟到消息改变该日输入 fingerprint，重算该日的会话和摘要，不以“当天已算过”跳过。

### 4.4 更新和删除的同步可见性

更新时同事务标记相关已发布对象 stale 并触发重算；旧正文允许作为明确标注的历史版本临时查看，默认搜索不将其当最新结果。标题、时间或分组变化同时更新旧、新范围。

删除时，`_purge` 必须在移除依赖前取得受影响对象：同事务撤下相关正文、摘要、块和搜索入口，安排剩余成员的 scope 重算。聚合对象即使还有其他成员，也不能让包含已删除内容的旧摘要继续被读取。只依靠 inputs 的外键级联是不够的。

删除与正在运行的模型任务竞争时，generation 与输入存活校验阻止旧结果重新发布。没有剩余内容的对象撤回；source tombstone 继续阻止旧备份重放。发布和删除保持同一锁顺序，必须用真实 PostgreSQL 并发验证，不能仅凭 SQLite 测试宣称正确。

### 4.5 调度与运维

复用 `personal-data-hub-collectors.service` 和现有 scheduler 的子进程监督，增加加工 drain 任务类别。采集和加工使用独立并发额度，初版加工最多一个 Worker，模型再独立限流；不使加工占满采集槽位。

加工 Worker 使用拟新增 `hub process-pending`，一次处理有界任务后退出；scheduler 再按队列状态触发。初期开发和回填可手动执行，日常运行接入在生命周期验证后切换，不引入第二个采集调度器或新消息中间件。

采集状态沿用原状态接口，加工状态使用独立汇总。来源页显示最近检查成功、最近收到数据、最近加工成功、待处理/失败/过期数量和覆盖。无新增记录不等于故障，未知覆盖不填写虚假的百分比。

## 5 来源加工实现要求

### 5.1 文档 Memos 日报和已有记忆

Memos 从 normalized.content 与 raw 中的实际标签、关系、附件提取正文。解析日报/周报标题、日期和段落，保留用户内容；顶部元信息不重复堆在正文中。文档阅读支持多级标题、段落、列表、引用、链接和实际存在的附件。短笔记保留原文，不强制生成摘要。

日报 cron 的用户原话、确认内容和报告按真实保存位置引用；仅有模型转述时注明产物性质，缺少回答依据不重新向用户采集。Hermes 日志与业务正文分离，无正文的执行日志只进入状态页。Mem0 已有内容保留 metadata、时间与可用外部出处，不在本轮产生新事实、自动纠错或记忆写入。

第一份贯穿样例使用合成的长 Memos 日报，包含 Markdown、附件、更新和删除；私有真实样本只在受控环境核验，正文不提交到仓库。

### 5.2 微信会话与邮件

微信以现有 person_id 隔离同名对象，保留方向、真实发言人、消息类型、时间和媒体。消息原始身份优先使用已有 source_message_key 等可核验字段，兼容旧 event 身份；不能只用“文本相同”去重，也不能把群聊都视为对象本人发言。

日会话的排序以真实时间和稳定消息键确定，超长消息可以分块但能完整拼回。媒体缺失、加密图片和不支持内容有明确占位，不能假装完成解码；原件入口继续可用。

长会话按真实时间间隔生成可折叠段。微信模型主题、要点与摘要提炼暂缓，留到后续分析模块统一设计，不作为本轮采集加工或验收条件。旧实现和已有结果只作后续参考。

邮件优先复用现有邮件服务提取出的正文与附件；只在当前归档字段不足时回到已有只读来源补齐。HTML 由后台转换为安全阅读结构，不在客户端直接执行 HTML。重复引用折叠但原文保留，可靠线程信息不足时退回单封邮件。

### 5.3 Mac 活动与录音

Mac 先解析实际 metadata 与上游摘要结构，把标题、描述、正文分区和时间组织成 activity，不将 frontmatter 原样当正文。6 小时与 10 分钟摘要按覆盖关系选用，实际原始片段用作依据和缺口，不重复计为多段活动。

原始 AX/UI 事件可按其真实字段归并，不能仅根据摘要字数、文件修改时间或流量估计活动时长。无活跃/离开字段时标明活动观察范围；不把来源背景记忆当作当日新活动。

Plaud 从已有 recording_id、转录和日产物关联阅读对象。分源草稿、正式融合稿、日摘要分别标明内容范围，日摘要不能直接当作单份录音摘要。仅使用有效时间戳提供音频定位，跨块说话人身份不擅自合并。本轮不重做现有 ASR、融合、重试队列。

### 5.4 数值与业务对象

将当前 display 与 daily_push 中需要共用的健康、财务、用量规则抽取为纯计算服务，旧接口和新阅读模型调用同一实现；根据已有测试保留业务日期、累计去重、重叠区间、Decimal 和币种分组语义。规则差异先按真实源类型确定，不通过统一外观掩盖分类差异。

metric_day 返回结果与完整组成引用，图表日点可以下钻。缺失与零不同，来源优先级和测量范围不同的网络数据不直接相加。现有任务快照只能展示当前任务和可观察历史，不构造过去每日待办量。

日历、任务、账单、Git、联系人采用专有字段和控件。Git 先加工当前实际取得的提交及来源链接，PR 等依照后续采集能力接入；当前采集成功不说明已覆盖全部协作事件。设备配置、订阅设置和 collector_gaps 用于状态或相关模块，不作为普通内容刷屏。

### 5.5 历史与辅助内容

`source_artifact` 等泛型需要按实际路径/文档类型识别，已知报告进入 document，结构化诊断进入辅助阅读，不凭文件存在宣布有可读业务内容。未知内容保留归档入口并出现在未支持类型清单，必须确定处理方案或明确范围调整后才能关闭来源验收。

## 6 内部读取接口与客户端迁移

### 6.1 拟定内部接口

| 接口 | 输入与输出 |
| --- | --- |
| `GET /api/v1/contents` | source、type/variant、时间、query、limit、cursor；返回公共头、状态和 next_cursor |
| `GET /api/v1/contents/{id}` | 返回类型化元数据、当前 revision 和正文/附件/依据入口，不直接包含整个 raw |
| `GET /api/v1/contents/{id}/blocks` | revision、cursor、响应预算；返回有序块及续页信息 |
| `GET /api/v1/contents/{id}/evidence` | 分页返回完整输入 ID/hash、角色和有效原件入口 |
| `GET /api/v1/processing/status` | source 和处理类型；返回积压、失败、版本与最近完成情况 |

复用原 viewer/API 只读鉴权，原 `records / timeline / dashboard / trends / recording content` 接口保持兼容。新接口不在本轮注册为新的 MCP 工具。

详情正文绑定 revision，读取中更新或删除时返回明确的 `content_changed / content_removed`，客户端刷新或撤下内容，不能把不同版本消息块拼在一起。列表使用基于时间与稳定 ID 的游标，属于实时浏览；迟到内容在刷新时出现，不宣称列表是永久冻结历史快照。游标绑定筛选条件，条件变更重新开始。

### 6.2 检索与性能

索引来自完整已加工正文和类型字段，返回命中块、摘录和定位信息。首版中文检索可以沿用规范化文本的字面匹配，必须限定来源或时间范围、限制返回量并实测实际数据规模；不能用前 500 字预览替代全文。

若实测不满足查询预算，再选择有依据的中文索引方案。语义搜索和独立检索服务不作为第一份阅读链路的前置。只在客户端即将显示时读取正文，原件和附件按需展开；列表 SQL 不选择大正文/原始载荷列。

### 6.3 客户端接入

新增 ReadingModels，显式区分 `content_id` 与旧 `record_id`，不将聚合 ID 交给 `/records/{id}`。按类型路由文档、会话、活动、录音、指标和业务详情，复用现有播放器、图表、附件和加载组件。

先为已支持类型切换阅读页，未迁移类型继续旧入口并登记待办，不能因此算采集侧已验收。unknown schema 有明确提示与原件入口，不显示空白后标记成功。返回字段和正文不再依赖客户端猜 raw/normalized 名称。

用户路径按类型验收：打开 Memos 长文并搜索中段；展开微信主题到原消息；活动摘要到时段依据；录音摘要到转录/音频；图表到组成；查看加工中和失败内容。每条路径必须在实际 Mac 客户端验证，NAS 接口返回不能代替真机阅读结果。

## 8 新来源接入流程

本轮先按[来源加工模板](templates/source-processing-profile.md)记录草案，经过 M1–M3 的实际加工与阅读验证再固定为团队规范。

1. 登记来源账户、实例、权限、采集范围、记录身份、时间、粒度、更新/删除及历史能力。
2. 取得代表样本，区分用户内容、辅助记录、原始事件、当前快照与上游加工产物。
3. 先明确用户最后读到什么，选择已有 type/variant；新类型必须同时定义 schema 和控件。
4. 实现或修复采集与提交回执，验证分页、水位、去重、补漏；保留源端真实语义。
5. 实现加工 profile、scope、来源链、索引和更新/删除行为。
6. 接入客户端完整阅读路径及诊断状态。
7. 用同一套样例验证采集、加工、阅读与生命周期，补真实受控样本验收。
8. 登记运行配置、版本、覆盖、恢复方法与验收记录；通过后标记来源就绪。

只完成步骤 4 的来源标为“归档可用”，不能标为采集侧交付完成。新增 kind 没有 profile 时进入未支持清单，不能自动落入通用 JSON 后悄悄通过。

Git 收口优先验证近期采集修复及持续运行，再扩范围；手机在分析完成后按实际平台形成独立增量计划；NAS 基于已有来源专项方案验证 Emby 和 Navidrome，保留快照与真实事件的差别。来源只提供状态快照时，阅读层描述“观察到的活动”及缺口，不编造精确开始/结束和完整时长。

## 9 验证 迁移与上线

### 9.1 测试与真实阅读验收

| 验证组 | 必需场景 |
| --- | --- |
| 文档 | 中文、Unicode 分隔、NUL 原件、长 Markdown、正文中段搜索、附件/关系缺失、日报与日志区别 |
| 会话 | 同名不同人、群聊发言人、完全相同但独立消息、超长消息、跨午夜、未知时间、迟到、对象改绑 |
| 模型加工 | 结果格式异常、引用不存在、遗漏/错误概括、超时重试、输入已变化、删除时仍在运行 |
| 存储与并发 | 原件与队列同事务、旧任务回写、租约抢占、崩溃恢复、profile 升级、编辑后旧/新 scope、聚合成员删除 |
| 指标 | 累计重复、重叠睡眠、午夜边界、Decimal、多币种、转账/待确认/未知、网络范围、未知与零 |
| 查询与客户端 | 鉴权、来源限制、游标筛选、revision 变化、正文完整分页、旧入口兼容、unknown schema、请求代次保护 |
| 运行 | 无新增数据、加工积压、单源失败不阻塞其他来源、回填限流、服务重启恢复、历史缺口保留 |

沿用已有合成 checks，新规则加入相应回归而不是重复堆测试。锁、队列、删除并发及索引在隔离 PostgreSQL 上验收；SQLite 仅用于不依赖数据库并发特性的快速检查。微信模型提炼的测试与质量评估留到后续分析模块，不计入当前简单验收。

代码库不保存真实个人正文与令牌，私有样本验收记录只保留安全的范围、版本、结论和问题。Mac 真机读取、分页、播放与更新撤下是独立验收项；没有真机结果时仅将客户端体验保持待验收，不阻塞服务端收口和后续开发。

### 9.2 增量迁移与回填

通过显式、幂等的加工模块迁移增加新表和索引，记录 schema 版本；不重建 hub_records，不依赖启动时隐式改大表。DEV-0 同时把新加工数据接入现有备份清单；原件、修正记录和不可重建状态按既有备份策略保护。

上线先装新表与兼容代码，再启用选定 profile 入队，样例验证后回填用户近期阅读窗口，随后补齐本轮历史范围。采用按稳定 record_id 和范围 key 的可恢复遍历，不能只按 observed_at 当回填游标，因为重复观察会移动它。入队开关先开启，回填期间新变更同样被捕获；增量与回填的 generation/fingerprint 防止倒退。

已实现维护命令：`hub process-pending --limit 50`、`hub processing-status`、`hub rebuild-content --source SOURCE --processor PROCESSOR`。回填支持 `--after`、`--limit`、`--one-page` 和 `--force`；当前没有 `--kind` 或 `--since` 参数。rebuild 只重建选定加工结果，不删除来源原件和水位。

2026-10-13 性能修复：日常调度默认关闭历史全量巡检。普通来源及阅读加工默认每 6 小时一个批次；Emby 保留 60 秒当前会话采样。历史维护显式使用上述定向重建命令；`--background-page` 仍在入队事务中保存位置和规则版本，同版本已有加工关系只查元数据，版本变化或 force 才完整核对原件。未完成的历史位置保留，新数据继续通过归档钩子入队。

新阅读页按类型切换，不全站一次改造；全部本轮类型迁移后才通过总验收。旧 preview/display_index 在兼容期继续维护，不能把旧客户端或既有 MCP 一起切坏。

### 9.3 发布与回退

复用现有正式部署入口、身份、密钥、配置与卷。按受影响业务模块发布；采集故障修复中的未提交改动需要与其负责人集成核对，不借本方案重置这些文件。

回退关闭新加工调度/入队与新阅读入口，保留原件、原采集水位及期间的源变更。回退读取入口不是回滚生产数据库。删除继续清理已有加工副本，即使后台加工暂停也不允许旧内容重新可读；这条钩子保留在回退兼容代码中。回切后重建需要覆盖暂停期间变化和删除。
