# M3：当前来源加工交付

本阶段在现有加工队列上接入邮件、活动、录音、指标、业务对象和辅助记录，不开发 Mac 控件、不增加模型调用、不新增采集来源。按用户最新要求，本阶段不新增或运行功能测试，采集侧完成后统一简单验收。

## 已实现

- email-v1：完整正文分块；HTML 只转文本，不输出可执行标签或外部资源；明确引用行可折叠；保留邮件身份与附件，不按主题猜线程。
- activity-v1：解析摘要前置信息和正文分区，把既有背景与当天观察区分；原始 AX/选中文本按真实事件读取，引用连接已有片段归档。缺少可靠覆盖关系时不估计活跃时长，也不累计摘要标签的时长。
- recording-v1：复用已有单份录音、分源转录、按日融合稿和日摘要；保留草稿和覆盖状态；音频时间跳转使用既有段时间和关联录音时长，分块说话人身份不合并。
- metric-day-v1：按来源、业务日期、时区和测量范围建立日对象。健康保留样本及去重依据，睡眠/运动区间取并集、累计步数/热量取有效最大值；账单按币种和类型分类，用 Decimal；用量按设备累计快照；网络按既有小时粒度且隔离采集点。所有组成从块和证据接口分页读取。
- business-v1：日历、任务、Git 提交、联系人、事实、提醒和非微信交流各有专有字段。Git 仅呈现实际已有提交，采集插件修复仍在 M4。
- source-status-v1：Hermes JSON 执行状态、Plaud 处理状态、缺口、配置及实验归档作为辅助信息。修复 Hermes JSON 被 document-v1 当作缺失正文的路由问题。实验/原始产物只提供原件和可识别字段，不称为业务内容。
- document-v1 升级 profile 2：增加既有 Mem0 文本和历史复盘产物，沿用完整分块与来源引用。不写回 Mem0、不生成新的长期分析。
- metric_rules：旧 display、daily_push 和新日指标复用健康提取/计算、财务分类/汇总和用量求和规则。未知账单类型不再被旧仪表盘算成收入；缺失数值不补成零。

## 共用链路变化

支持一个源记录对应多个日 scope（健康快照可能含多天样本），以及转录的关联录音输入。沿用已有更新、删除、成员关系、hash/revision 和发布校验；不改原件字段、持久卷或身份。

`/api/v1/contents` 增加 type 筛选；默认日常列表排除辅助状态和原始电脑观察。processing/status 给出来源的加工规则和 business/auxiliary/unsupported 阅读策略。块分页、全文检索和证据入口保持原契约。

## 交付边界

当前活动摘要不能证明精确的覆盖区间或活跃时长；来自摘要的背景不是当天新增事实。录音可读性依赖现有产物真实完成状态，不将 pending/draft 伪装成完整。内部实验文件和来源依据采取辅助归档策略，完整原件继续可取。

历史回填使用既有调度器遍历和后台队列。本阶段不把“加工已接入”描述为全量历史已经加工完成，也不以接口代替 Mac 阅读验收。客户端需求见 [m3-current-sources.md](client-requirements/m3-current-sources.md)。

下一阶段按既定顺序进入 M4：根据 M1–M3 的实际加工方式整理接入流程，修复 Git 采集，再接 Emby、Navidrome。手机继续放在分析之后；外部 MCP/事件推送继续放在采集链路完成之后。
