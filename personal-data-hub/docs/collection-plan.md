# 采集模块增量设计

日期：2026-10-11。状态：设计方案，未据此修改采集代码、配置或运行服务。

本轮沿用现有采集基座，完成来源范围和数据语义的约定、现有故障与覆盖核验，以及 NAS 重点服务活动接入。采集模块负责可靠保存来源实际提供的信息，为后续整理和应用提供依据；不承担记忆推理、长期分析和客户端业务设计。

手机采集后续再做，本轮不设计手机应用、后台机制或专用接口。主观状态和建议反馈继续使用现有日报 cron，不增加手工记录要求。

## 1 本轮范围

| 工作 | 本轮要做的事 | 完成边界 |
| --- | --- | --- |
| 既有采集 | 核对现有修复、来源范围、分页和补采结果 | 数据可持续入库；当前故障与历史缺口分开说明 |
| Git | 核对插件故障修复与提交采集完整性，明确 PR 等协作事件的接入范围 | 提交采集可靠；新增事件按类型单独验收 |
| 日报与 Mem0 | 复用已有读取路径，核对原始回答、确认结果和来源信息是否保留 | 能定位已有内容；不再采集一遍，不在采集器中生成新记忆 |
| NAS 活动 | 第一批接 Emby、Navidrome；随后按需接 Komga、Wallabag | 保存实际活动事件或明确标记的状态快照 |
| 对外提供 | 继续使用既有来源状态、记录、详情、附件 API/MCP | 新记录可查、可追溯；可读聚合与分析接口由上层负责 |

不新增通用插件框架、消息中间件、独立数据库或第二个采集调度器；不以搜集更多来源作为本轮完成条件。Memos 客户端写入和 Mem0 检索调优是独立应用任务，采集侧只负责读取和归档其源端结果。

## 2 现有链路与需要补的部分

现有 NAS 拉取路径为 `适配器 → Record/Batch → runner → Store → PostgreSQL/附件`；推送来源通过既有 webhook 或 `/api/v1/ingest` 提交。Mac 继续使用现有 Agent、稳定文件交付、校验与归档回执。

| 能力 | 已有实现或记录 | 本轮处理 |
| --- | --- | --- |
| 来源注册和记录身份 | `source + external_id` 生成稳定记录 ID，来源账户不可直接改绑 | 保留已有 ID；新增账户或实例使用独立来源 ID |
| 版本与去重 | 内容哈希、记录修订、附件哈希 | 复用，不新增一套事件存储 |
| 采集调度 | 当前代码已有独立来源进程、并发上限、超时、退避和中断恢复 | 核对现有修复验收，新增来源加入原调度 |
| 水位 | 整轮成功后提交；此前已入库批次可在重跑时去重 | 保留，明确各来源水位语义 |
| 删除 | 显式删除、权威完整清单、删除墓碑 | 新来源默认不按查询缺失删除历史 |
| 来源状态 | 当前运行结果、错误原因和历史质量问题 | 复用，补来源覆盖说明，避免用记录数量冒充完整性 |
| 对外读取 | 来源、记录列表、详情、正文和附件工具 | 新类型走原接口，增加必要预览即可 |

现有部署文档已经记录 2026-10-11 Git 等来源在新调度下成功运行；这不等于已验证连续运行或 PR 覆盖。当前 `GitCollector` 实际调用的是 `get_me` 和 `search_commits`。本轮以这些具体边界立项，不重复建设已经补上的调度能力。

| 日报用户输入与确认 | 原日报流程产物，经已有归档路径接入 | 先定位当前存储位置与引用；已在 Memos 中的内容不另建重复来源 |

NAS 已发现 `embyserver`、`navidrome`、`komga`、`favsync-wallabag-1` 正在运行。Emby 当前使用 host 网络，Navidrome 和 Komga 使用 `media_net`，Wallabag 使用其现有独立网络。适配器优先从现有宿主采集进程访问既有可达入口，不为接入统一网络或搬迁容器；实际业务鉴权与响应字段在实现时核对。

## 4 每个来源必须说明的最小契约

继续使用现有 `Record` 和 `Batch`，不先发布新的通用协议。每个来源在说明和样例中写清以下六项：

1. **采集范围**：账户、实例、记录类型、历史窗口、过滤条件，以及明确不覆盖的部分。
2. **记录身份**：源端稳定 ID；没有事件 ID 时，说明如何生成可重试的快照身份。重试同一批数据不得临时换 ID。
3. **时间含义**：实际发生、源端更新与本次观察分别表示什么；未知发生时间保持为空，不能用采集时间冒充。
4. **更新方式**：追加事件、可变对象、累计快照或当前状态；原始事件与估算结果不能混写。
5. **增量与删除**：分页、水位、回看窗口、完整清单边界、删除能力和不可恢复缺口。
6. **内容与质量**：最小 `normalized` 字段、原始载荷、附件要求、字段缺失及错误时的行为。

通用字段仍放 `Record`；服务相关字段放 `normalized`。新增活动类型建议保留 `service`、`source_user_id`、`item_id`、标题、服务原链接、会话或播放器 ID，以及源端实际提供的进度、状态与观察时间。缺失字段不猜测填充。

`raw` 保存实际返回的业务载荷，不保存请求凭据和认证头。接口未返回原始回答时，只能归档日报正文或模型转述并标注来源，不能把转述重新标记成用户原话。

源端对象的新版本继续更新同一记录并保留修订；当前播放观察等快照则使用观察身份，不能只用内容 ID 覆盖所有历史。相同内容被再次播放不是重复事件，必须保留时间或会话差异。来源账户沿用显式配置，不能仅凭展示名自动合并不同用户。

## 5 NAS 活动接入

统一归类为 NAS 服务活动，底层仍按服务维护小适配器。读取业务接口优先于日志和数据库；确需读取数据库时采用已有一致快照方式，避免直接把正在写入的文件当静态文件复制。

### 5.1 Emby

- 首版读取当前会话的用户、设备、正在播放条目、暂停状态和进度，归档为 `media_playback_snapshot`。
- 建议先以 60 秒为可调采样间隔，空结果也记录本轮检查成功；没有播放时不生成伪播放记录。
- 会话接口返回的内容可能涉及多名用户，适配器按配置的源端用户 ID 过滤后归档。远程控制权限筛选不等同于“只有该用户的活动”。
- 若现有实例确有可靠的播放事件或历史接口，再追加 `media_playback_event`。实现前核对可用性，不把安装插件或改造 Emby 作为首版前提。
- 当前进度可因跳转、暂停和倍速变化。采集端不根据两个进度点推算真实观看时长，也不把某次会话消失写成确定的停止事件。

官方 `getSessions` 提供当前会话、`NowPlayingItem`、用户及播放状态；它本身不是完整播放历史接口。[Emby 会话文档](https://dev.emby.media/reference/RestAPI/SessionsService/getSessions.html)

### 5.2 Navidrome

- 首版复用其支持的 `getNowPlaying`，按当前用户过滤，归档为 `music_playback_snapshot`；保留歌曲、歌手、专辑、播放器及实际返回的时间或状态信息。
- 建议从 60 秒采样开始；播放器是否上报、报告是否陈旧需要用实际使用的客户端核对。
- Navidrome 官方说明：调用 `stream` 不会将歌曲记为已播放，播放记录依赖 `scrobble` 的提交。因此读取空结果不能直接说明没有听音乐，下载或音频请求也不能当作已收听。
- 不为采集调用写入型 `scrobble`，以免制造播放记录。历史次数或最近播放时间可作为源端状态保存，但不能据此展开成缺少时间依据的逐次事件。

能力依据：[Navidrome API 支持范围](https://www.navidrome.org/docs/developers/subsonic-api/)和 [getNowPlaying 返回语义](https://opensubsonic.netlify.app/docs/endpoints/getnowplaying/)。协议示例中的可选扩展字段不代表当前实例一定支持。

### 5.3 阅读来源

Emby 和 Navidrome 路径验收后，再按同样方式接 Komga、Wallabag，避免四个服务同时扩大验证范围。

| 来源 | 目标记录 | 首版边界 |
| --- | --- | --- |
| Komga | 指定用户的阅读进度、完成状态及源端更新信息 | 是否存在可用的增量与历史接口需验证；进度是状态，不等于阅读时长 |
| Wallabag | 收藏条目、标签、归档/已读状态和修改信息 | 收藏不等于阅读，归档状态不证明完整读完；正文是否已有其他归档先核对 |

MoviePilot、下载器、刮削和转码服务暂不作为消费活动来源。需要时可独立采集“新增媒体”“下载完成”等管理事件，并保留对应含义，不混入观看或收听记录。

### 5.4 覆盖承诺

首版承诺保存成功采样时看到的状态，不承诺完整播放历史或精确时长。短于采样间隔的活动、未上报的播放器、服务离线期间的活动都可能缺失。来源只提供当前状态时，不进行虚假的历史回填；已有可靠历史来源时才补历史。

将快照归并成可读活动片段、跨来源去重或估计时长，属于后续整理模块；原始快照始终保留其观察语义。

## 6 Git 修复与范围补齐

先核对现有插件调用是否持续成功、失败原因是否清晰、分页和实际返回是否完整，再扩充数据类型。

1. **提交记录**：保留现有来源和 `repo + sha` 身份。明确按作者和提交时间查询的范围，不能声称覆盖所有本地仓库或所有贡献行为。
2. **增量窗口**：当前实现将初始 `window_start` 持续保存在水位中，查询范围会逐渐扩大。改进方向为固定本轮上界、从已完成窗口带重叠回看地推进；结果超过搜索上限时分割时间窗口，窗口全部完成才推进水位。
3. **上限与迟到**：时间切分后仍超过上限，应继续按受管仓库等范围切分或明确失败，不能无限重试同一查询。较晚推送的旧时间提交可能落在回看窗之外，需对受管仓库设置较宽对账窗口或显式补采，不宣称重叠窗口可以保证找回任意历史。
4. **PR 等协作记录**：优先增加用户创建的 PR 及其当前状态，随后接用户参与的评审和 Issue。它们分别保存源端 ID 和更新时间，不能从 commit 猜测 PR 是否合并或评审是否完成。
5. **查询来源**：优先使用现有 GitHub MCP 支持的工具；缺少必要能力时评估原授权是否可用的官方只读接口，不另建一个 GitHub 业务 MCP。搜索缺失不用于判定删除。

新增 PR 等记录时可保留对象状态历史；若要精确的状态转换时间，应读取源端事件，不能用 Hub 首次观察时间代替。Git 故障修复和新增协作类型分别验收，避免修复任务无限扩展。

## 7 水位 补采与失败处理

- **保持现有提交原则**：来源锁防止并发写入同一来源；归档成功后才推进水位。整轮失败时，已入库部分保留，重跑通过稳定 ID 和哈希去重。
- **明确回执能力**：现有 HTTP 接口在提交后返回 `committed`，`batch_id` 目前是回显，不是完整的持久批次去重账本。本轮继续依靠记录身份去重，不引入新的批次平台，也不宣称跨网络恰好一次交付。
- **更新不能倒退**：补采可变对象时应读取其当前版本；来源提供可比较版本时拒绝旧版本覆盖新版本。只有快照、没有可靠版本的来源需要单写者和源端对账，不能仅凭请求到达顺序判断新旧。
- **完整清单才做删除对账**：当前 `authoritative` 会作用于整个来源，只适合完整同范围清单。不能把最近一天、某个用户子集或单页查询标记为完整清单；新 NAS 来源默认不开启这一删除模式。
- **失败分类**：网络和限流复用自动退避，并遵循上游提供的重试时间；授权失效和接口格式变化保留具体原因，避免高频无效重试。数据格式异常不丢弃原始证据或伪造空结果。
- **历史缺口独立保留**：缓存轮转或源端没有历史导致无法补齐时，保存缺口说明。新的成功运行可以恢复正常状态，但不抹掉旧缺口。
- **附件失败可见**：正文已归档与附件完整分别表述；不能把缺失附件当作完整成功。续传和重试沿用对应来源既有机制。

运行状态继续使用现有 `ok / partial / failed`。来源页至少能区分最近检查成功、最近收到数据、当前失败和历史缺口；无新增记录并不等于失败，最近检查成功也不证明历史齐全。通知继续复用既有采集异常通知流程。

## 8 开发拆分与顺序

本轮可拆成三个开发任务；先完成范围清楚的部分，不先重构公共基座。

| 任务 | 负责范围 | 首次交付 |
| --- | --- | --- |
| COL-1 既有来源收口 | 来源范围说明、Git 稳定性及窗口修复、日报与 Mem0 字段保真核对 | 可验证的现有来源清单、必要修复和样例；PR 类型扩展另列子任务 |
| COL-2 NAS 媒体与音乐 | 新薄适配器、Emby/Navidrome 配置样例、快照记录及必要预览 | 两个真实来源可持续归档，明确采样限制 |
| COL-3 NAS 阅读 | Komga/Wallabag 的能力核对及薄适配器 | 在 COL-2 的方式验证后接入阅读状态；缺少能力时记录明确边界 |

COL-1 和 COL-2 可并行；注册入口、公共配置和少量预览分支由一个集成方合入。新 NAS 适配可以放在独立的 `src/personal_data_hub/nas_activity.py`，接入现有 `runner.adapter()`；先不把全部旧采集器拆目录。COL-3 延后，不是首批交付前置条件。

应用凭据、用户映射和服务地址放在现有私有配置位置，仓库仅保存无秘密的样例。继续使用原采集 systemd 服务和现有 PostgreSQL、附件目录；本方案不要求改 NAS 服务镜像、网络、挂载或部署入口。

## 9 验收

首批验收只覆盖实际改动，不重跑无关业务：

1. 同一批来源记录重跑不重复，真实修改产生修订；旧补采不覆盖较新的可变对象。
2. 分页中断、超时和限流后水位正确，其他来源仍能继续；Git 超限不会静默截断。
3. 一次真实 Emby 播放和一次真实 Navidrome 播放能取得相应快照；暂停、重复播放、空闲和未上报按实际能力说明，不伪造完整事件。
4. NAS 仅归档配置的个人账户，库中存在、下载、播放状态和历史事件的含义明确。
5. 日报已存在的回答和 Mem0 内容能通过归档定位，不要求用户重复输入，也不在采集器中生成新解释。
6. 新记录可通过现有 API/MCP 列表和详情读取，原件及必要字段保留；历史缺口与当前运行状态分开。
7. 生产接入只更新受影响的采集配置与代码，保留已有身份、凭据、任务入口和持久数据。

采集模块到此交付可信的来源记录和覆盖边界。如何合并成时间线、建立个人基线、分析和提供建议，继续按[全局架构](target-architecture.md)由上层模块完成。
